## 1. Current state: single-tenant by env

JAMES today is **single-tenant by env var**. The boundary is
`JAMES_WORKSPACE`:

- `core/plugins/workspace.py::get_workspace_root` resolves a path
  from `JAMES_WORKSPACE` (unset → project root; set → that path).
- `config.py` reads it once at import-time and the four data dirs
  (`RAW_DIR` / `WIKI_DIR` / `UPLOAD_DIR` / `CHROMA_DIR`) all live
  under that root.
- Audit log path follows the same convention via `JAMES_AUDIT_DB`
  (default = `<workspace>/audit.db`).
- 100+ import sites across the codebase use the resolved path
  constants directly — they do not know which workspace they're in.

**Implicit invariant**: the operator runs **one JAMES process per
workspace**. Two tenants = two processes, two configs, two ports.

**This works** for current scope: Hashevolution dogfooding, local
deployment, single-customer pilot. It fails as a SaaS pattern.

---

## 2. Why "one process per tenant" doesn't scale

| Cost surface | Single-tenant pattern | Multi-tenant SaaS |
|---|---|---|
| Memory | N processes × (model + embedder + Chroma client) | Shared model + embedder; per-tenant Chroma |
| Cold start | One process to warm | Warm once, route per-tenant |
| Audit log path | One file per process | One DB, tenant-scoped rows |
| Approval gate | One operator identity per process | Per-tenant operator identity, verified |
| Cross-tenant leak risk | Process-isolated → zero | Per-row tenant_id discipline → audit-evidence-grade |

The SaaS pattern is **process-shared, data-isolated**. That requires
two additive contracts: a **tenant identifier** that flows from
boot through every audit-write call, and an **approval-evidence
binding** that names the principal at the OS / IdP level instead of
trusting a free-form string.

## 3. Tenant-id contract (G1)

### 3.1 Scope

Add an **optional** `tenant_id` field to every emitted audit row,
read at boot from `JAMES_TENANT_ID` (process-level) **and** override-
able per call site for code paths that legitimately cross tenants
(e.g., admin tooling). Downstream replay filters by `tenant_id`
when set; behaves as v0.5 (no filtering) when unset.

### 3.2 Shape

```python
# core/lifecycle/tenant.py — NEW module (proposed)

JAMES_TENANT_ID_ENV: Final[str] = "JAMES_TENANT_ID"

def current_tenant_id() -> Optional[str]:
    """Process-level tenant id from JAMES_TENANT_ID env. None if unset."""

def with_tenant_id(tenant_id: str) -> ContextManager[None]:
    """Context manager that overrides the process tenant id for the
    duration of the `with` block. Thread-local. Use for admin
    tooling that legitimately writes audit rows on behalf of a
    specific tenant from a process without a single ambient tenant."""

def is_tenant_isolation_enforced() -> bool:
    """True iff JAMES_REQUIRE_TENANT_ID env var is set. When True,
    every audit-row emit MUST resolve a non-empty tenant_id (process
    env OR with_tenant_id) or the emit returns False (matches the
    'never raises' contract of replay_audit)."""
```

### 3.3 Emit-side wire-in

```python
# core/lifecycle/replay_audit.py — emit_lifecycle_event extension

def emit_lifecycle_event(
    event_type: str,
    payload: Dict[str, Any],
    *,
    user_role: str = "system",
    timestamp: Optional[str] = None,
    db_path: Optional[str] = None,
    retention_class: Optional[str] = None,   # v0.5 G4 (landed)
    tenant_id: Optional[str] = None,         # v0.5 G1 (proposed)
) -> bool:
    # Resolve tenant_id from: explicit arg → with_tenant_id stack →
    # process env. If JAMES_REQUIRE_TENANT_ID is set and resolution
    # yields None, return False (no row inserted).
    # On success, tenant_id is stamped into event_payload JSON under
    # the key "tenant_id" — no schema migration required.
```

### 3.4 Replay-side wire-in

```python

    tenant_id: Optional[str] = None,   # v0.5 G1 (proposed)

```

### 3.5 Storage strategy

`tenant_id` lives inside the existing `event_payload` JSON column
(same approach as G4's `retention_class`). **No schema migration**.

Rationale: the audit_log schema was already designed with a JSON
`event_payload` column precisely so additive fields like this don't
churn the schema. Mirrors `retention_class` (G4 landed) — same
pattern.

### 3.6 What G1 explicitly does NOT promise

- **Not cross-tenant query prevention.** A misconfigured admin
  caller can still pass `tenant_id="other"` and read another
  tenant's rows. The contract surfaces the boundary; enforcement
  is the caller's responsibility (handled separately by RBAC at
  the HTTP layer, not by this primitive).
- **Not row-level encryption.** Tenant-id is a routing token, not
  a confidentiality boundary. Confidentiality requires the
  next layer (encrypted-at-rest, separate keys per tenant), which
  is genuinely deferred to v1.0+ when customer threat model is
  known.
- **Not multi-process safety.** One process can serve multiple
  tenants via `with_tenant_id`; multiple processes still need OS-
  level mutex on the SQLite file (existing v0.5 limitation).

## 4. Verified approver principal (G2)

### 4.1 Scope

`core/change_request.py` requires an `approver_username` string in
the audit log before a self-evolution change can auto-apply. The
string is operator-written and unverifiable after the fact. G2
proposes a **principal-binding layer** that captures the identity
evidence alongside the username so the approval is cryptographically
attestable.

### 4.2 Shape

```python
# core/security/approval_evidence.py — NEW module (proposed)

@dataclass(frozen=True)
class ApprovalEvidence:
    principal: str             # canonical principal name
    source: Literal["posix", "oidc", "ssh", "explicit"]
    evidence_hash: str         # sha256 of the evidence blob
    captured_at: str           # ISO timestamp
    expires_at: Optional[str]  # for time-limited tokens

def current_approval_evidence() -> Optional[ApprovalEvidence]:
    """Best-effort identity binding from the current process.
    Resolution order: explicit override (JAMES_APPROVAL_PRINCIPAL +
    JAMES_APPROVAL_EVIDENCE) → OIDC discovery (when configured) →
    POSIX getpass.getuser() floor → None.
    """

def require_approval_evidence() -> bool:
    """True iff JAMES_REQUIRE_APPROVAL_EVIDENCE is set. Production
    SaaS sets this to 1; local-dev leaves it unset (current default
    behaviour preserved)."""
```

### 4.3 Change-request wire-in

```python
# core/change_request.py — apply_change_request extension

def apply_change_request(
    cr_id: str,
    *,
    approver_username: str,             # existing v0.4 contract
    approval_evidence: Optional[ApprovalEvidence] = None,  # G2 (proposed)
) -> bool:
    # When require_approval_evidence() is True and
    # approval_evidence is None or the captured principal doesn't
    # match approver_username, reject the change-request apply.
    # When require_approval_evidence() is False (current default),
    # behaviour is byte-identical to pre-G2 — preserves v0.5
    # local-dev ergonomics.
```

### 4.4 Resolution sources

| Source | When it fires | Evidence hash content |
|---|---|---|
| `explicit` | `JAMES_APPROVAL_PRINCIPAL` + `JAMES_APPROVAL_EVIDENCE_B64` env both set | Operator-provided blob (e.g., signed JWT base64-encoded) |
| `oidc` | OIDC discovery URL configured + valid token | `sub` claim + `iat` + `aud` |
| `posix` | Default fallback on systems with `getpass.getuser()` | `pwuid` + uid + gid |
| `ssh` | `SSH_TTY` env present (active SSH session) | `SSH_TTY` + `SSH_CLIENT` |

The fallback chain matches the **availability** of identity
sources: SaaS deployments configure OIDC; local-dev gets POSIX
identity; CI gets explicit. The chain stops at the first source
that returns a complete `ApprovalEvidence` — no silent fallthrough.

### 4.5 What G2 explicitly does NOT promise

- **Not MFA enforcement.** The evidence captures the principal;
  MFA at the IdP is upstream. JAMES checks the IdP's signed
  attestation, not the user's 2FA state directly.
- **Not key escrow.** Evidence is stored as a hash, not as
  recoverable plaintext. A lost or rotated OIDC key is the IdP's
  concern.
- **Not approver-list enforcement.** "Who CAN approve" is RBAC
  at the HTTP layer; G2 binds "who DID approve" to a verifiable
  principal. RBAC + G2 compose at the call site.

## 5. Tenant + approver composition

G1 and G2 compose **orthogonally**. A SaaS audit row from a
post-rollout state looks like:

```json
{
  "edge_id": "e_edge_abc123",
  "mutation_type": "superseded",
  "retention_class": "7y",
  "tenant_id": "tenant_acme_corp",
  "approval_evidence": {
    "principal": "alex@acme.com",
    "source": "oidc",
    "evidence_hash": "sha256:...",
    "captured_at": "2026-08-15T14:23:11Z"
  }
}
```

Each field is independently optional. Backwards-compatible at every
phase. No schema migration. The `event_payload` JSON column carries
all four fields as additive keys.

## 6. What this memo does NOT cover

- **HTTP-layer RBAC** — separate concern. JAMES today defers HTTP
  auth to the operator's reverse proxy (nginx + OIDC, etc.). G1/G2
  provide the audit-trail surface; HTTP enforcement is upstream.
- **Encryption at rest** — separate cycle; depends on customer
  threat model. Tenant-id is a routing token, not a confidentiality
  boundary.
- **Workspace path migration** — `JAMES_WORKSPACE` env pattern is
  preserved. SaaS deployments may still use one workspace per
  process for hard data isolation; tenant-id adds **soft isolation
  WITHIN** a shared process.
- **Quota / rate-limiting per tenant** — separate cycle; orthogonal
  to identity.
- **Vertical-specific tenant policies** — BLOCKED per rule #1.
