## 1. Verdict

The current lifecycle surface is **structurally enterprise-ready** for
single-tenant deployments. Eight (8) gaps are identified below that
matter for multi-tenant SaaS deployments or for explicit enterprise
audit-evidence requirements. Of these:

- **G1, G2, G7** are **scope-aligned**: must address before any
  external customer pilot (Stream D gate). They concern audit
  evidence and cross-tenant safety — not optional polish.
- **G3, G4, G5** are **strongly recommended**: enterprise ergonomics
  that the operator catches in dogfooding but that don't block first
  pilot.
- **G6, G8** are **deferred to v1.0**: design-locked-after-LOI
  decisions; documenting now to avoid silent drift.

No gap requires backwards-incompatible schema changes. All eight are
additive surfaces.

## 2. What's working (enterprise-ready primitives)

### 2.1 Deterministic memory lifecycle (T1 + T7 + T2 + T6)

The four lifecycle modules compose into a deterministic, LLM-free
state machine for fact mutation:

- **T1** (`schema.py`): every source has `valid_from` / `valid_until`;
  every edge has a `validity` window + `status.active` + `mutation_type`
  enum (`active` / `invalidated` / `superseded` / `expired`).
- **T7** (`supersede_chain.py`): contradictions that represent the
  world genuinely changing produce a new edge with the old edge's
  `status.superseded_by` pointing to it. `walk_supersede_chain` is
  cycle-detecting (raises on insertion-bug cycles), and
  `reconstruct_view_at(t)` returns the byte-identical edge state at
  any past time `t`.
- **T2** (`contradiction_arbiter.py`): the LLM-free 4-rule decision
  tree (B_supersede / A_invalidate / ignore / B_supersede-default)
  is the Mem0 differentiator. Audit-replay-safe because the
  classifier is deterministic.
- **T6** (`causality.py`): foundational-vs-corroborative semantics
  (T6.C.b refinement) — hard deps (transitive/inferred) any-empty
  invalidates; soft deps (operator) only weaken when hard deps survive.

**Enterprise value**: a customer auditor can replay the system at any
past audit cutoff and see byte-identical state. Contradictions don't
require LLM re-judgement — the classifier output is the same on
2026-06-12 as on 2027-06-12 given identical inputs.

### 2.2 Document-level interpretive layer (v0.5 B.5)

- **DOCUMENT_SUBTYPES** (10 horizontal: contract / policy / procedure /
  memo / report / specification / meeting_minutes / standard / form /
  record). Vertical-agnostic.
- **4 new RELATION_TYPES**: AUTHORED_BY, APPROVED_BY (sensitive=True),
  REFERENCES, DERIVED_FROM (transitive=True).
- **ENTERPRISE_ROLES** (4: AUTHOR / REVIEWER / APPROVER / READER) —
  pure permission data, orthogonal to the baseline RBAC.
- **DocumentLifecycleState** (7: DRAFT / IN_REVIEW / APPROVED / PUBLISHED /
  SUPERSEDED / ARCHIVED / REVOKED) — interpretive layer; T7 chain
  still owns transition truth.
- **`apply_document_subtype_filter`** — R1-R5 evidence-of-absence
  contract at the subtype level.

**Enterprise value**: a "which policy is currently in force?" query
routes through deterministic intent classification, never silently
drops the policy slot even when zero policies match, and always
reads the current edge head via `reconstruct_view_at(now)`.

### 2.3 Audit-trail primitives

- **`replay_audit.py`** + **`replay_graph.py`** materialize the
  audit log into a graph state at any time `t`. `RAB v0.1.1`
  (DOI [10.5281/zenodo.20625533](https://doi.org/10.5281/zenodo.20625533))
  measures this surface — JAMES AC/RF/PC = 1.000/1.000/1.000 vs
  vanilla baseline 0.275/0.000/0.000 on scenario S1.
- **Self-evolution approval gate**: `core/change_request.py` requires
  `approver_username` in the audit log before auto-apply. Cannot be
  bypassed without a separate code change.

**Enterprise value**: maps directly to EU AI Act Articles 10 / 12 /
19 (apply from 2026-08-02 per Art. 113). The audit-replay surface is
not aspirational — it's measured and DOI-archived.

## 3. Gaps (enterprise readiness)

### G1 — Tenant-scoped audit log (must-address for SaaS)

**Current state**: The audit-log path is workspace-scoped via the
`JAMES_WORKSPACE` env var. There is no in-process tenant identifier;
a multi-tenant operator must isolate at the process/container level.

**Enterprise gap**: SaaS deployments routinely co-locate tenants in
one process for cost reasons. The current audit-log writers (in
`replay_audit.py` and the various lifecycle modules) do not stamp
`tenant_id` on emitted rows. A tenant-A misconfiguration that leaks
into tenant-B's audit replay is silently undetectable.

**Recommended additive surface** (no schema break):

- Add an optional `tenant_id` field to the audit-log row emitter
  (default unset → behaves as v0.5).
- Add a `JAMES_TENANT_ID` env var that the emitter reads at boot.
- Document the contract: "if `tenant_id` is set, downstream replay
  filters by tenant_id; if unset, all rows are visible (single-tenant
  mode, the v0.5 default)."

**Why must-address**: the EU AI Act audit-evidence surface is the
load-bearing customer-facing claim. A cross-tenant audit leak in
v0.6 would be a credibility-breaking incident.

**Scope alignment**: B.2 (multi-tenant workspace isolation review,
queued in v0.5 entry doc) will fold this gap into its design memo.

### G2 — Approver identity is a string, not a verified principal

**Current state**: `core/change_request.py` requires
`approver_username` in the audit log before auto-apply. The
`approver_username` is a free-form string the operator writes to
the audit row.

**Enterprise gap**: a string field cannot be verified after the fact.
A compromised operator (or a misconfigured automation) can write any
value to `approver_username` and bypass the human approval gate
without leaving a forensic trail.

**Recommended additive surface**:

- Bind `approver_username` to an OS-level / identity-provider
  principal (e.g., POSIX `getpass.getuser()` floor + optional
  OIDC `sub` claim when configured).
- Add a `approval_evidence` field to the audit row that captures
  the principal-binding evidence (e.g., the OIDC token hash + iat).
- Reject change-request apply when `approval_evidence` is missing
  AND `JAMES_REQUIRE_APPROVAL_EVIDENCE=1` is set.

**Why must-address**: this is the **structural integrity** of the
self-evolution gate. If the gate can be lied to, the gate doesn't
exist. The current single-tenant local-first usage masks this — every
operator IS the principal — but the first SaaS pilot exposes it.

**Scope alignment**: lands as a separate `feat/v0.6-approval-evidence`
PR after dogfooding identifies the most natural principal source
(POSIX vs OIDC vs SSO vs custom). No backwards-incompatible change.

### G3 — `reconstruct_view_at(t)` is per-edge, not per-corpus

**Current state**: `supersede_chain.reconstruct_view_at(head,
predicate, t)` returns the edge state at time `t` for ONE chain
head. Replaying an entire corpus state at time `t` requires the
caller to enumerate all chain heads and call `reconstruct_view_at`
for each.

**Enterprise gap**: this is fine for replay-on-demand (an auditor
asks "what was edge X at time T?") but doesn't scale to a "show me
the complete corpus state at audit cutoff T" query. The naive O(N)
enumeration scales poorly for corpus > 10⁵ chain heads.

**Recommended additive surface** (R5 follow-up; not blocking pilot):

- Add `reconstruct_corpus_view_at(t, *, limit=None)` that streams
  edge heads in pages, applies `reconstruct_view_at` per head, and
  yields `(head_id, edge_at_t)` tuples.
- Document the asymptotic cost: O(N × avg_chain_length) where
  N = number of chain heads. Operator picks `limit` for paged
  retrieval.

**Why strongly recommended**: the EU AI Act Article 12 evidence
expectation ("at any point in the system's lifetime") implies
corpus-wide reconstruction. The primitive exists at edge level;
collecting it into a corpus-level convenience function is pure
additive ergonomics.

**Scope alignment**: lands when an enterprise auditor request
materializes (likely Stream D pilot kickoff). Not blocking.

### G4 — Approval evidence has no machine-readable retention policy

**Current state**: audit rows are append-only and never deleted.
This is the right semantic for replay-safety, but enterprise
deployments often have legal retention windows (e.g., 7 years per
G2's [doc_002_policy_data_retention] in the v0.5 fixture).

**Enterprise gap**: there is no machine-readable retention-policy
attachment to audit rows. The retention decision is operator-side
(file-system housekeeping); JAMES has no contract for "this row
is past retention; safe to archive to cold storage."

**Recommended additive surface**:

- Add an optional `retention_class` field to the audit-row emitter
  (values: `permanent`, `7y`, `3y`, `pilot`, `custom:<iso8601>`).
- Add a `pending_retention_review(now)` predicate that returns
  the rows that have passed their retention window.
- DO NOT add an auto-delete path. The decision to actually delete
  is a separate approval-gated change request (preserves the
  audit-replay-safety invariant).

**Why strongly recommended**: GDPR Art. 17 (right to erasure) is
the most common enterprise customer follow-up question after the
EU AI Act audit-evidence story. Having a primitive ready is a
~3-day implementation that materially shortens the first-pilot
legal-review cycle.

**Scope alignment**: lands when Stream D LOI scopes the retention
profile. Not blocking dogfooding.

### G5 — No batched contradiction-arbiter call

**Current state**: `contradiction_arbiter.classify(...)` takes one
(old_edge, new_fact) pair and returns one label. Ingest pipelines
that process N facts call the function N times.

**Enterprise gap**: enterprise ingest commonly batches (e.g., a
nightly bulk-load of 10k documents). The current per-call surface
is correct but doesn't expose the batched call site needed for
trace-id-correlated bulk audit rows.

**Recommended additive surface** (low priority):

- Add `classify_batch(pairs)` that returns a list of labels in
  the same order. Trivial wrapper; pure perf hint, not semantic.
- Add an `audit_batch_id` to the emitter so a bulk ingest's
  contradiction decisions group naturally in audit replay.

**Why strongly recommended**: bulk ingest is enterprise's first
real load test. Having batched trace correlation in v0.5 means
the first pilot's bulk-load audit replay is immediately legible.

**Scope alignment**: enterprise nice-to-have. Lands when the first
bulk-ingest customer signal materializes. Not blocking.

---

### G6 — Cross-document `DERIVED_FROM` transitivity not measured

**Current state**: `DERIVED_FROM` is registered as transitive in
the B.5.b RELATION_TYPES table. The B.5.b fixture (doc_007 derived
from doc_006) exercises a single-hop chain. T6 causality cascade
(`causality.py`) handles edge-level derivation invalidation but does
NOT currently propagate through document-level `DERIVED_FROM`.

**Enterprise gap**: "if a base contract is revoked, do derived
specifications get flagged?" — the answer requires document-level
transitive walk that doesn't exist yet.

**Recommended deferred surface**:

- Mother-level work: extend T6 cascade to walk
  `DERIVED_FROM` document-level chains. This is **structurally
  vertical-agnostic** (any document type can be derived from any
  document type).
- BUT — the test corpus + measurement evidence requires real
  customer data (which docs are actually derived from which).
  Without that, we'd build a hypothetical primitive untested
  against any actual mutation pattern.

**Why deferred to v1.0**: lands after Stream D LOI when customer
data tells us what `DERIVED_FROM` chains look like in practice.
Premature design = premature optimization.

**Scope alignment**: noted here so it doesn't silently drift into
v0.5 cycle work.

### G7 — Cross-process supersede-chain race not protected

**Current state**: `supersede_edge(old_edge, new_fact, ts)` mutates
the old edge's `status` field in place + returns a new edge dict.
The caller is responsible for writing both back. No advisory lock
is acquired.

**Enterprise gap**: two concurrent processes (e.g., a scheduled
ingest job + an interactive operator commit) can both observe the
same `old_edge`, both call `supersede_edge`, and both write back.
The second write silently overwrites the first; one supersede event
is lost.

**Recommended additive surface**:

- Add an optimistic-locking layer via an `etag` (or `version`)
  field on the edge dict. `supersede_edge` reads `old_edge.etag`,
  bumps it on the new edge, and the writer rejects writes whose
  base etag doesn't match the on-disk etag.
- Document the contract: "if etag mismatch, caller retries with
  the current head" (standard optimistic-concurrency pattern).

**Why must-address**: as soon as v0.5 enables any scheduled-job
ingest path (which dogfooding will), this race becomes reachable.
Single-tenant local-first usage masks it because the operator is
the only writer.

**Scope alignment**: lands as a `feat/v0.5-etag-optimistic-locking`
PR. Touches `supersede_chain.py` + `schema.py` (adds the field).
Mother-level — applies to every edge type, not just document edges.

### G8 — No ontology-pack mount surface (v1.0 freeze gate input)

**Current state**: `DOCUMENT_SUBTYPES` and `RELATION_TYPES` are
module-level Python dicts. To add a vertical pack (e.g., the
legal pack scoped by a hypothetical LOI), an external collaborator
would have to either edit `core/ontology.py` directly or maintain
a fork.

**Enterprise gap**: the v1.0 plugin-API-freeze gate requires a
**stable mount surface** for ontology packs. Today there is no
documented contract. CLAUDE.md rule "no plugin API stability
promises before v0.3" was respected; v0.5 is the natural place to
START documenting the future shape (without promising stability
yet).

**Recommended deferred surface** (v1.0 freeze gate input):

- Document the proposed shape in a v0.6 design memo BEFORE
  building it. Sketch:
  ```python
  from core.ontology import register_subtype_pack
  register_subtype_pack(
      pack_id="legal-v1",
      subtypes={...},
      relation_types={...},
      requires_capability="rule_one_exemption_granted",
  )
  ```
- The `requires_capability` gate is the v1.0 mechanism that
  prevents accidental vertical-pack mount during the
  v0.5-mother-platform cycle.

**Why deferred to v1.0**: any concrete shape we lock now risks
needing to break in v1.0. Documenting the future shape is enough
for v0.5; building it without an LOI is premature.

**Scope alignment**: B.3 (plugin API stability review, queued
in v0.5 entry doc) will produce the v0.6 design memo.
