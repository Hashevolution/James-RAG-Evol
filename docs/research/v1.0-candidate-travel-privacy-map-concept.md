## 1. 질문 (r2)

> 회사가 JAMES를 운영하면서, 소비자가 선택한 여행지·상품·식당 등을 기록하고,
> 이를 알고리즘화시켜 향후 추천 상품화하고, 그것으로 광고 효과 등 매출로도
> 연결시킬 수 있는 플랫폼화가 가능한가?

## 2. 한 줄 결론 (r2)

**가능하다 — 그리고 r1보다 JAMES의 실제 운영 모델에 더 잘 맞는다.** JAMES의
권한 체계(admin/manager/employee/external), 배포 모델, v0.5 방향(기업 내부지식
ontology)이 전부 "회사가 운영하는 시스템"을 전제하므로, r2는 v0.5 enterprise
방향과 **구조적으로 동형**이다 (내부 지식 → 고객 선택 지식으로 코퍼스만 교체).

단, 정직한 경계가 하나 있다: **추천 엔진·광고 서빙·attribution 스택 자체는
JAMES 범주 밖이다** (ARCHITECTURE §2 비목표: real-time transactional DB 아님,
booking 시스템 대체 아님 — "다운스트림 제품" 영역). JAMES가 플랫폼화에
기여하는 것은 그 위가 아니라 그 **아래**: 소비자 선택 데이터를
**"동의-증명 가능하고(consent-clean), 정정 가능하고, 추천 사유를 replay로
증명할 수 있는 1st-party 데이터 자산"** 으로 만들어 주는 신뢰 백본이다.
2026-08-02 EU AI Act 발효 + 국내 개인정보보호법 환경에서 이 백본이
광고·추천 사업의 **규제 차익(regulatory moat)** 이 된다 — 같은 데이터로
경쟁사는 못 하는 개인화를 "증빙 가능하게" 한다는 것이 r2의 차별화 논지다.

## 3. r1 → r2 모델 역전에서 유지되는 것 / 바뀌는 것

| 축 | r1 (소비자 소유) | r2 (회사 운영) |
|---|---|---|
| 데이터 컨트롤러 | 소비자 (per-user vault) | **회사** (회사의 JAMES 인스턴스) |
| JAMES 배포 | 소비자 기기/개인 인스턴스 (운영 난이도 上) | 회사 단일 배포 — **현재 아키텍처 그대로** |
| "선택형"의 의미 | 내 데이터를 내가 통제 | **동의 관리**: 소비자 opt-in 상태가 정책으로 강제되고 감사로 증빙됨 |
| 개인정보 프리미티브의 역할 | 제품 정체성 (주권 역전) | **규제 모트** (consent-clean 데이터 자산화) |
| 수익 모델 | 소비자 구독 (미검증) | **추천 상품화 + 광고 — 검증된 업계 모델** 위에 컴플라이언스 차익 |
| 시장 리스크 | "주권"이 구매 동인인지 미입증 | 모델 자체는 검증됨; JAMES 기여분의 가치가 미입증 (§7) |

핵심: r1의 프리미티브(소유권 격리·추상화·정정권·replay)는 r2에서 **버려지지
않고 역할이 바뀐다** — 소비자 보호 장치에서 회사의 컴플라이언스 증빙 장치로.

## 6. "알고리즘화"와 자기진화 게이트 — 충돌이자 판매 포인트

운영자 요구의 "알고리즘화 → 추천 상품화"가 추천 로직의 **자동 학습·자동
배포**를 의미한다면 CLAUDE.md rule 3 (자기진화 = 승인 게이트 필수)과 충돌한다.
그러나 이것은 약점이 아니라 r2의 판매 포인트로 뒤집힌다:

- 추천 알고리즘 변경 = self-evo proposal → 인간 승인 → 배포, 전 과정 감사 기록
- ML 반복 속도에는 마찰이지만, **"우리 추천 알고리즘의 모든 버전 변경은
  승인자와 함께 기록되어 있다"** 는 광고·추천 거버넌스(알고리즘 투명성 규제,
  다크패턴 규제) 대응에서 경쟁사가 흉내 내기 어려운 속성
- 절충 형상: 모델 학습/실험은 다운스트림에서 자유롭게, **프로덕션 추천 정책
  교체 시점만** JAMES CR 게이트 통과

## 7. 매출 연결 — honest framing (`memory/feedback_finding_size_honest_framing.md`)

- **검증된 부분**: "소비자 선택 기록 → 추천 → 광고 매출" 모델 자체는 업계
  표준이다. r1과 달리 시장 존재 증명이 불필요.
- **미입증 부분 (JAMES 기여분)**: ① consent-clean·설명가능 추천이 광고
  단가/전환율/규제 리스크 비용에서 측정 가능한 차익을 만드는가, ② 그래프 기반
  추천 품질이 PoC 수준을 넘는가. 둘 다 branching 시점 사전등록 측정 대상
  (Direction α 교훈: 가치를 가정하지 말고 빌드와 함께 증명).
- **범주 정직성**: JAMES가 광고 플랫폼이 되는 것이 아니다. JAMES는 광고·추천
  플랫폼이 올라타는 **신뢰·증빙 레이어**이고, 매출 기여는 직접이 아니라
  차익(컴플라이언스 비용 절감 + 프리미엄 데이터 자산) 경로다.

## 8. v1.0 후 branching 시 도메인 팩 최소 형상 (r2)

1. **여행 ontology** — POI·상품·식당·소비자 세그먼트 어휘 (CR-E 경로로 등재)
2. **결정-이벤트 인입 adapter** — 외부 행동로그 파이프에서 선택/구매 이벤트만
   lifecycle 이벤트로 변환 (R6 저신뢰 콘텐츠 경로 준수)
3. **Geo adapter + 이중 뷰** — 소비자용 지도, 회사용 세그먼트/추천 경로 대시보드
4. **동의 관리 팩** — opt-in 상태 ↔ PolicyEngine 정책 바인딩 + 소비자 UI
5. **추천 다운스트림 인터페이스** — 외부 recommender가 그래프를 읽고, 추천
   결정만 audit로 회수하는 typed interface
6. **제휴 egress 프로파일** — abstraction 모듈의 광고 네트워크용 정책 프리셋

전부 `packs/travel/` + 다운스트림 경계 안. mother 수정 0건이 목표 형상.
