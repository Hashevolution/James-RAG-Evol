## 1. 질문

> 비주얼라이징 된 체계 + JAMES 구조를 여행업계가 쓴다면, 개인정보 관리를
> 중심으로 맞춤형 여행지나 맛집 등 지도를 비주얼라이징하는 계획을 세울 수
> 있도록 하는 **선택형 소비자 중심 서비스**로 발전시킬 수 있는가?
> 깊이 있게 튜닝 가능한가?

## 2. 한 줄 결론

**가능하다 — 그리고 의외로 잘 맞는다. 단, 잘 맞는 이유가 "여행"이 아니라
"개인정보 주권" 쪽에 있다.** 이 컨셉의 차별화 모트는 전부 이미 존재하는
플랫폼 프리미티브(소유권 격리·정책 게이트·egress 추상화·정정권·replay 감사)에서
나오고, 여행 도메인 자체에서 나오는 것은 거의 없다. 따라서 이것은
mother-platform 논지를 **역으로 검증하는 사례**다: 얇은 도메인 팩만으로
branching 가능한 버티컬의 형상을 정확히 보여준다.

기존 여행 서비스(OTA, 지도 앱, 추천 플랫폼)의 모델은 "플랫폼이 내 취향
프로필을 소유하고, 나는 그 대가로 추천을 받는다"이다. JAMES 구조는 이걸
뒤집을 수 있다: **취향·제약·이력은 내 로컬 vault에 남고, 외부로는 추상화된
질의만 나가며, 모든 추천은 "왜?"를 replay로 증명할 수 있다.** 이 역전이
서비스의 정체성이고, 그 역전을 가능하게 하는 부품이 이미 v0.4에 있다.

## 3. 자산 매핑 — 컨셉의 요구사항 vs 이미 있는 것

| 서비스 요구사항 | 기존 플랫폼 프리미티브 | 위치 |
|---|---|---|
| 내 취향/이력/제약(알레르기·건강·동행·예산)은 내 것 | 소유권 격리: `uploaded_by` 추적, `/artifacts/mine/*` 스코프, 비소유자 404 (존재 누설 차단) | `core/data_artifacts.py`, ARCHITECTURE §6 |
| "선택형(opt-in)" — 내가 허락한 것만 쓰인다 | 메모리 scope 승격은 명시적 사용자 액션만 (session→workspace 자동 승격 금지) | `core/memory/store.py`, ARCHITECTURE §5.7.6 |
| 외부(클라우드/제휴사)로 내 정보가 안 나간다 | egress 추상화 MASK/PASS/KEEP_LOCAL: 민감 엔티티는 typed placeholder로만 egress, 역매핑은 로컬 전용, KEEP_LOCAL은 거부 | `core/abstraction/` (4-file, §5.7.13), `_runner.py` keep_local 거부 |
| 누가 내 데이터를 봤는지/왜 이 추천이 나왔는지 증명 | append-only audit + `reconstruct_graph_at(t)` replay; RAB AC/RF/PC 결정론적 메트릭 (LLM judge 없음), EU AI Act Art.10/12/19 매핑 | `core/lifecycle/replay_graph.py`, `eval/rab/SPEC-v0.1.md` |
| 내 프로필이 틀렸으면 내가 고친다 | Change Request: 제안→검토→승인, self-approval 금지, audit에서 전체 재구성 가능 | `core/change_request.py`, ARCHITECTURE §5.6 |
| 역할/맥락별 정보 노출 제어 (동행자 공유 등) | PolicyEngine 4-gate (retrieve/walk/tool/emit) + 출력단 PII 마스킹 | `core/policy_engine.py`, `core/security_layer/_abac.py` |
| 취향 프로필 자체의 표현 | trait 저장 + correlation ripple (11-trait radar) — 여행 취향 프로필로 일반화 가능한 구조 | `core/character_profile/_profile.py` |
| 그래프 기반 비주얼라이징 | 3D force graph + reasoning path pulse 애니메이션 + trace 사이드바 | `frontend/graph.html`, `frontend/static/graph.js`, `chat.js` trace poll |

**해석**: 표의 좌측 열은 "개인정보 중심 소비자 서비스"가 요구하는 신뢰 계약의
거의 전부다. 우측 열은 모두 도메인 중립 프리미티브다. 여행 서비스가 필요로
하는 신뢰 스택을 JAMES는 **이미 도메인 중립으로 보유**하고 있다.

## 4. 갭 분석 — 없는 것과 그 귀속

| 갭 | 내용 | 귀속 | 난이도 |
|---|---|---|---|
| **Geo 레이어** | 좌표 스키마, 지도 렌더링(Leaflet/Mapbox류), geo 질의 — 현재 코드베이스에 전무. 3D 그래프는 추상 공간이지 지리 공간이 아님 | 도메인 팩 (UI adapter) | 중 — 그래프 노드에 geo attribute 추가 + 지도 뷰는 기존 frontend 패턴 위 신규 뷰 |
| **일정 계획 엔진** | JAMES는 retrieval+reasoning이지 constraint solver가 아님. 시간창·동선·예약 가능성 최적화는 별개 문제 | 도메인 팩 (또는 외부 솔버 tool 연동 — 기존 tool sandbox 경로 활용) | 중상 |
| **신선 외부 데이터** | POI·영업시간·리뷰는 로컬 코퍼스가 아니라 라이브 피드. 단, **Direction α 측정 교훈 주의**: cloud tier 가치는 reasoning 품질에선 미입증이었다 (`reports/research-runs/alpha-8-cloud-tier-extension-20260604.md`). 여행에서의 cloud/외부 가치는 reasoning이 아니라 **data freshness**이므로 별개 명제 — 그래도 측정으로 입증해야지 가정하면 안 됨 | 도메인 팩 (커넥터) + 기존 §5.7.12 egress trust zone 재활용 | 중 |
| **소비자급 UX** | 현 frontend는 operator/admin 급. 소비자 모바일 UX는 다른 제품 표면 | 도메인 팩 | 상 |
| **배포 모델** | local-first 원칙을 소비자에게 그대로 가져가면 "per-user vault (on-device/개인 인스턴스) + 추상화 질의만 서버로" 구조 — 가장 차별적이지만 운영 난이도 높음. 멀티테넌시는 현재 `JAMES_WORKSPACE` env 수준 | 플랫폼 (v1.0 게이트 D 차원과 동일 항목) | 상 |

**핵심 관찰**: 갭 5개 중 플랫폼 본체를 건드리는 것은 배포 모델 하나뿐이고,
그것도 이미 v1.0 게이트(멀티테넌시/SSO)에 들어 있는 항목이다. 나머지는 전부
도메인 팩 경계 바깥에 격리 가능하다. 즉 **"튜닝"의 형상은 mother 수정이 아니라
얇은 팩 + 어댑터**다 — 이것이 이 컨셉이 v1.0 branching 모델과 정합하는 이유.

## 5. 차별화 논지 (vs 기존 여행 서비스)

1. **프로필 주권 역전** — Google Maps/OTA는 취향 프로필을 플랫폼 자산으로
   축적한다. 이 컨셉은 프로필을 사용자 로컬 자산으로 두고, 추상화 레이어가
   "PERSON_1, CONSTRAINT_1(알레르기), BUDGET_1" 수준의 placeholder만 내보낸다.
   결정론적 마스킹(§5.7.13 invariant 1)이므로 egress 자체도 감사·재현 가능.
2. **설명 가능한 추천** — "왜 이 맛집인가?"에 대해 추천 시점 t의 그래프 상태를
   `reconstruct_graph_at(t)`로 복원해 추천 경로를 byte-level로 재현. 블랙박스
   추천과의 범주적 차이이며, RAB의 AC/RF/PC가 그대로 소비자-facing 신뢰
   지표가 된다. EU AI Act (2026-08-02 발효) 매핑이 이미 되어 있어 규제
   정합성이 마케팅이 아니라 측정 가능한 속성.
3. **정정권의 제품화** — "내 프로필에서 이 기록 지워/고쳐"가 CR 프리미티브로
   감사 가능한 워크플로가 됨. GDPR/개인정보보호법의 열람·정정·삭제권을
   기능이 아니라 아키텍처로 보유.
4. **선택형의 구조적 보장** — opt-in이 약관 문구가 아니라 scope 승격 규칙
   (자동 승격 금지)과 PolicyEngine fail-closed로 강제됨.

## 6. 정직한 리스크 (honest framing — `memory/feedback_finding_size_honest_framing.md` 적용)

- **소비자 시장 검증 부재**: "개인정보 주권"이 여행 소비자의 실제 구매 동인인지
  미입증. 기술 fit ≠ 시장 fit. 이 문서는 기술 타당성만 다룬다.
- **추천 품질 자체는 미측정**: JAMES의 graded-answer 한계는 cycle γ에서 보았듯
  retrieval/selection 쪽 벽이 있다 (unsupervised supporting selection). 추천
  품질이 기존 플랫폼 대비 경쟁력 있다는 증거는 없음 — branching 전 측정 필요.
- **로컬-퍼스트 소비자 배포는 업계 전반에서 어려운 문제**: 동기화, 백업, 기기
  분실 시나리오 등. 가장 차별적인 속성이 가장 비싼 속성.
- **Direction α 교훈의 직접 적용**: "외부 tier가 가치 있을 것"이라는 전제를
  빌드와 함께 증명하지 않으면 안 된다. 여행판 전제 = "신선 데이터 피드가
  로컬 코퍼스 대비 추천 품질을 실제로 올린다" — 사전등록 측정 대상.

## 7. v1.0 후 branching 시 도메인 팩 최소 형상 (설계 스케치만)

1. **여행 ontology** — POI 타입, 음식/제약 어휘, 동행 관계 (시스템 scope 등재는
   CR-E 경로)
2. **Geo adapter** — 엔티티 geo attribute + 지도 뷰 (기존 graph.js 패턴의 자매 뷰)
3. **데이터 커넥터** — POI/영업시간 피드, §5.7.12 trust zone 통과 + R6 저신뢰
   콘텐츠 경로(`extract_data_only`) 준수
4. **취향 프로필 팩** — character_profile trait 체계의 여행 인스턴스화
5. **일정 솔버 tool** — 기존 tool sandbox로 격리된 외부 constraint solver

전부 `packs/travel/` 경계 안. mother 수정 0건이 목표 형상.
