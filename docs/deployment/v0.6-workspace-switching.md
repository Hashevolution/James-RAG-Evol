# Workspace Switching — Operator Runbook (v0.6.1)

> **Status**: Operator-facing runbook for the v0.6.1 workspace badge +
> launcher script. Self-contained — no LLM / measurement / customer
> action involved.
>
> **Use case**: Stream A.3 dogfooding wants a clean measurement
> baseline (0 → N entity over 1 month) without throwing away the
> 313+ entity that already live in the default workspace. JAMES'
> per-workspace data layout (`JAMES_WORKSPACE` env, v0.3 ship)
> already makes this possible — this doc is the *UX layer* that
> makes it ergonomic.
>
> **CLAUDE.md compliance**: workspace separation is a horizontal
> mother-platform capability (zero domain content). Rule #1 unchanged.

---

## 1. Why switch workspaces?

| Scenario | Suggested workspace |
|---|---|
| Main project use — existing 313 entity + audit history | **default** (no `JAMES_WORKSPACE`) |
| **Stream A.3 dogfooding** — fresh baseline, 0 → N evidence | **`dogfood-<YYYY-MM>`** (launcher offers it automatically) |
| Cycle-γ / RAG benchmark research data | `workspaces/cycle_gamma_*` (already present) |
| Per-customer pilot data after LOI | `workspaces/<customer-id>` (Track D, LOI-gated) |

One JAMES server process = one workspace. Switching = restart with a
different `JAMES_WORKSPACE` env. Single-process multi-workspace routing
is v1.0 multi-tenant territory and out of scope here.

## 2. Launcher (`scripts/operator/start_james.{ps1,sh}`)

Interactive workspace picker that wraps the python server boot. The
env is set in the child-process scope only — your shell profile is
untouched.

### 2.1 Windows / PowerShell

```powershell
# Interactive — prompts a numbered list
.\scripts\operator\start_james.ps1

# Non-interactive — known workspace
.\scripts\operator\start_james.ps1 -Workspace dogfood-2026-06
.\scripts\operator\start_james.ps1 -Workspace default
```

The picker lists:

- `default` (the main workspace — 313 entity / chroma_db_bge_m3 / audit log under repo root)
- Every existing `workspaces/<name>/` that passes the path-safe pattern (`^[a-z][a-z0-9_-]*$`)
- A `NEW: dogfood-<YYYY-MM>` slot — selecting it auto-creates the dir

### 2.2 POSIX / bash

```bash
chmod +x scripts/operator/start_james.sh

# Interactive
./scripts/operator/start_james.sh

# Non-interactive
./scripts/operator/start_james.sh dogfood-2026-06
./scripts/operator/start_james.sh default
```

## 3. UI badge (`📁 <workspace>` in header)

Once logged in, every page (chat / workspace / admin) shows the active
workspace name in the header:

| Default workspace | Custom workspace |
|---|---|
| `📁 default` (neutral nav-btn) | `📁 dogfood-2026-06` (accented border — visually distinct so you notice you're not on main) |

The badge updates immediately after a successful login (auth.js calls
`window.JAMES_WORKSPACE_BADGE.refresh()`); no full page reload needed.

Tooltip shows the resolved absolute path + entity count for a
quick at-a-glance sanity check.

### 3.1 What the badge doesn't do

- **Switch workspaces in-place** — the server is per-process; switching
  requires a restart. Use the launcher (§2) for that.
- **Show counts other than the entity index** — chroma row count /
  audit-log size are intentionally out of scope (would be another
  endpoint per page load).

## 4. Dogfood workspace step-by-step (Stream A.3 first day)

1. **Choose** the new workspace via the launcher:
   ```powershell
   .\scripts\operator\start_james.ps1
   # Pick "NEW: dogfood-<YYYY-MM>"
   ```
2. **Verify** in the browser: header shows `📁 dogfood-<YYYY-MM>` (accented),
   workspace tab shows 0 entity, chroma index empty.
3. **Phone share-target** keeps working unchanged — the endpoint URL
   is the same (`/upload/`); the server just writes into the new
   workspace dir.
4. **Daily upload + RAG check** per Phase 2 of the dogfooding roadmap
   (`docs/handovers/v0.6-entry-skeleton-2026-06-13.md` §5.1 + the
   "사용자 경험 6 Phase 로드맵" discussion 2026-06-14).
5. **Switch back** to the main workspace anytime by stopping the
   server + relaunching with `-Workspace default`. The dogfood
   workspace files stay on disk under `workspaces/dogfood-<YYYY-MM>/`
   until you delete the directory manually.

## 5. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Badge stays hidden after login | `/workspace/info` 401 — token / api_key not in localStorage | Re-login. Open DevTools → Application → Local Storage to verify `james_token` is set |
| Badge shows `📁 default` after switching | The launcher set the env but you're connected to a *different* JAMES instance | Confirm the URL in the browser matches the launcher console output. Check Task Manager / `Get-Process python` for a stray instance |
| Launcher rejects workspace name | Pattern enforced `^[a-z][a-z0-9_-]*$` (mirrors `core/plugins/workspace.py::_TENANT_ID_RE`) | Use lowercase + digits + `-` / `_` only; start with a letter |
| Korean labels render as boxes in PowerShell | Windows PowerShell 5.1 default cp949 | Launcher sets `[Console]::OutputEncoding = UTF8`; if still broken, run from PowerShell 7 |
| Phone share-target uploads land in wrong workspace | Server was switched after the phone shortcut was tested | Re-test the share-target after the switch + verify the URL in the workspace badge tooltip |

## 7. Out of scope (intentional non-goals)

- **In-place workspace switching from the UI** (single-process multi-workspace routing). Belongs to v1.0 multi-tenant work
- **Workspace deletion from the UI** — delete `workspaces/<name>/` from the filesystem
- **Migration between workspaces** — separate Track A cycle if it ever becomes needed; out of scope for the dogfooding session
- **Per-tenant headers** — `JAMES_WORKSPACE_PER_TENANT` + `X-Tenant-Id` already shipped in v0.5 G1.a; this runbook is about *operator-side* selection, not tenant routing
