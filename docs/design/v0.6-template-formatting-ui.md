# v0.6 — Template Formatting UI (horizontal document-shaping engine)

> **Status: design-stage.** This memo defines a *horizontal* template
> engine: the user supplies a template at runtime, pastes raw content,
> and JAMES reshapes the content onto the template structure and hands
> back a downloadable file. JAMES ships **zero** templates. See §1 for
> the CLAUDE.md rule #1 boundary — this is the spine of the design.

## 1. Why this is mother-platform work, not a vertical (rule #1)

CLAUDE.md rule #1 forbids domain features (legal / food / retail /
travel / finance) before v1.0. A document-formatting feature is exactly
the kind of thing that *could* smuggle a vertical in. The boundary:

- ✅ **Allowed (this design):** a *horizontal* engine. Templates are
  **user data**, stored under the workspace (`templates/`), uploaded at
  runtime. The engine only maps "raw content → the user's template
  structure." It has no knowledge of what the template is *for*.
- ❌ **Forbidden:** shipping any built-in template (a contract form, a
  medical chart, a financial report) as a code asset or seed file. That
  is a domain pack and will be reverted in review.

**Mechanical test of compliance:** grep the repo after every PR in this
series — there must be **no template content** under `core/`,
`frontend/`, or any seed/fixture path. The only templates that ever
exist live in a *workspace* directory at runtime, created by an operator.
This mirrors the Track F "mother-level UI" classification in the v0.5
close handover: solo-doable, LOI-independent, because it adds a
horizontal capability, not a domain.

## 2. User-visible flow

1. Operator registers a **template** in the workspace via one of three
   input modes (§3): a markdown/text file, an image (OCR), or pasted
   text.
2. Operator pastes **raw content** into a panel and selects the active
   template.
3. JAMES runs one LLM pass that reshapes the raw content onto the
   template's structure (§5).
4. The result is rendered to a **downloadable file** (md / txt / html in
   v1; docx deferred) and registered as a data artifact (§6).

## 3. Template input modes (`ingest.py`)

All three modes converge on a single **raw template text** string, which
`spec.py` then parses into a `TemplateSpec`.

| Mode | Source | Path |
|---|---|---|
| `text` | pasted string | used verbatim |
| `file` | `.md` / `.txt` upload | decoded as UTF-8 |
| `image` | `.png` / `.jpg` / … | OCR via existing `tools/multimodal` (Tesseract) → text |

The image mode (PR-5) reuses the multimodal OCR stack already wired for
`/analyze/image/`; no new OCR dependency.

## 4. `TemplateSpec` — the parsed structure (`spec.py`)

A `TemplateSpec` is the normalized, domain-agnostic shape extracted from
the raw template text:

- **sections** — ordered list of headings / labelled blocks detected
  (markdown `#`/`##`, or `Label:` lines).
- **placeholders** — `{{name}}` / `{name}` / `[name]` tokens the author
  left as fill-in slots.
- **order** — declaration order is preserved (deterministic).
- **hints** — optional per-section length / style hints if present.

The spec is **data**. Any imperative-looking text inside a template
(e.g. "ignore previous instructions") is treated as template content,
never as a command to the formatter — see §7 (prompt-injection).

## 5. Formatting pass (`formatter.py`)

`format_content(raw_content, spec) -> str`:

- Builds a prompt that presents (a) the template structure from `spec`
  and (b) the raw content, instructing the model to *redistribute the
  content into the template's sections/placeholders without inventing
  facts*.
- Calls `llm.router.call_router(prompt, task_type="template_format",
  max_tokens=...)`. When cloud egress is enabled the call routes through
  the §5.7.12 trust zone like any other synth call.
- Returns the formatted text. The formatter does **not** add domain
  content — if the raw content lacks a section's data, the section is
  left empty / marked, not fabricated (grounding discipline consistent
  with the abstention work).

## 6. Output + storage (`render.py` + artifacts)

- `render(formatted_text, fmt) -> bytes` for `fmt in {md, txt, html}`.
  `html` is a minimal, escaped wrapper (no inline JS) so it is safe to
  open. `docx` is **deferred** (would add `python-docx`).
- Output bytes are written under `workspace_path("templates",
  "<template_id>", "out", "<out_id>.<ext>")` and registered via
  `core.data_artifacts` so the existing "my artifacts" surface lists
  them and the audit trail covers them.

## 7. Security & trust

- **Path safety:** template ids and output ids must match the
  path-safe identifier pattern already used for tenant/pack ids
  (`^[a-z][a-z0-9_-]*$` family). No path separators, dots, or
  traversal. Reuse the `core/plugins/workspace.py` validator shape.
- **Prompt injection:** the template and the raw content are both
  untrusted *data*. The formatter prompt frames them as data blocks;
  the system instruction is fixed and not user-overridable.
- **LLM egress:** pasted content goes to the LLM. With the local
  backend (default) this stays on-box. With cloud egress enabled, the
  call passes through `PolicyEngine` + the §5.7.12 abstraction trust
  zone — no new egress path is introduced.
- **Audit:** every `apply` call writes a `_write_audit(...)` row
  (template id, output artifact id, role, no raw-content body).
- **Authorization:** endpoints gate on `role` like `routes/artifacts.py`;
  templates are owner-scoped (self-view 404 on others' ids, mirroring
  the artifact authority model).

## 8. Module layout (rule #5 — each file < 20 KB)

```
core/templating/
  __init__.py      # public façade (re-export)
  store.py         # template CRUD under workspace_path("templates")
  spec.py          # raw template text -> TemplateSpec (sections/placeholders)
  ingest.py        # 3 input modes -> raw template text (text/file/image-OCR)
  formatter.py     # raw content + TemplateSpec -> LLM -> formatted text
  render.py        # formatted text -> output bytes (md/txt/html)
```

```
routes/templating.py   # create / list / detail / apply / download
```

## 11. Non-goals

- No shipped templates of any kind (rule #1).
- No `.docx` output in v1 (dependency cost; deferred).
- No template *versioning* / diff in v1 (a template is replace-on-edit;
  the Change Request primitive is a separate surface).
- No automatic ingestion of formatted output back into the knowledge
  graph — output is a deliverable file, not a corpus document, unless
  the operator separately uploads it.
