# v0.6.1 — LLM Routing Unification

> **Status: design + impl.** Operator catch 2026-06-15: the LLM stack
> has accumulated ~9 env vars and 4 dispatch layers, each with its
> own opt-in flag, with no single page that says *"this is what is
> currently routing what."* This PR consolidates the **decision
> surface** without changing the dispatch layers themselves.
>
> **Scope frame**: a *settings repository* + admin UI on top of the
> existing layers. We do NOT rewrite `llm/router.py`,
> `core/reasoning/router.py`, or `core/abstraction/`. We move
> *where the operator sets the knob* from "edit env + restart" to
> "edit Settings UI; DB-first with env fallback." Behaviour with no
> DB row is byte-identical to the current env-driven path.

### 1.4 Layer count
4 independent dispatch layers:
1. `llm/router.py` — task_type → model
2. `core/reasoning/router.py` — intent/scope auto-router
3. `core/reasoning/backends/*` — stage backend pin (synth / retrieve / verify)
4. `core/agent_tools/backends.py` — agent-loop backend (added in #920)

Each layer has its own toggle. An operator has to remember which env
sets which.

## 2. The unification principle

> **DB-first, env-fallback. Settings UI is the single source of
> truth. Env stays as the boot-time default for installs that have
> never written the DB row.**

- A new SQLite table `llm_settings` (in the existing `james_data.db`)
  with a key/value shape.
- A `core/llm_settings.py` repository: `get(key, env_fallback) ->
  str`, `set(key, value, *, by) -> None`, `as_dict() -> dict`.
- Every call site that currently reads an env var goes through the
  repository helper. The helper:
  1. Reads the DB row.
  2. If empty → reads the corresponding env var.
  3. If still empty → returns the documented default.
- Admin UI writes to the DB row. Env is never written from the UI.
  Operators who *want* env to be source-of-truth (CI runners, scripted
  deployments) leave the DB row empty.

### 2.1 What stays untouched

- Dispatch layers themselves (the 4 layers in §1.4). No code in
  `llm/router.py`, `core/reasoning/router.py`, `core/abstraction/`
  or `core/agent_tools/backends.py` changes its *logic*; only the
  *source of the value* it reads.
- `#model-chip` per-session override (it's already a session-only
  knob; not the operator-default knob).
- BLOCKED_PATH_PATTERNS, sandbox, audit — all orthogonal.

### 2.2 What changes

| Old (env-only) | New (DB-first via repo) |
|---|---|
| `os.environ.get("JAMES_LLM_MODEL", "gemma4:e4b")` | `llm_settings.get("default_model", "JAMES_LLM_MODEL", "gemma4:e4b")` |
| Same for `JAMES_CODING_MODEL`, `JAMES_AUTO_ROUTER`, `JAMES_AUTO_STYLE`, `JAMES_AGENT_BACKEND`, `JAMES_FORCE_CLOUD`, `JAMES_BACKEND_SYNTH`, `JAMES_AGENT_OLLAMA_MODEL`, `JAMES_AGENT_ANTHROPIC_MODEL` |

## 3. DB schema

```sql
CREATE TABLE IF NOT EXISTS llm_settings (
    key        TEXT PRIMARY KEY,
    value      TEXT NOT NULL,
    updated_at TEXT NOT NULL,        -- ISO-8601
    updated_by TEXT NOT NULL         -- admin username
);
```

Single-row-per-key. Keys are a fixed taxonomy (see §4); unknown keys
are stored but not consulted by the resolver — future-proofing for
extensions without a migration.

**Storage location**: `james_data.db` (existing, alongside the data-
artifacts table). No new DB file; matches the v0.5 "no unnecessary
SQLite proliferation" rule.

## 5. HTTP surface

| Endpoint | Auth | Body |
|---|---|---|
| `GET /admin/llm-settings/` | admin | — |
| `POST /admin/llm-settings/` | admin | `{api_key, settings: {key: value, ...}}` (partial-update; only specified keys are written) |

`GET` returns `{settings, env_fallbacks, defaults}` so the UI can
show the current effective value AND the env that would take over if
the operator cleared the DB row.

`POST` validates each key against the taxonomy. Unknown keys → 400.
Invalid value (e.g. `auto_router=maybe`) → 400. Audit row written.

## 6. Frontend — admin Settings panel

The existing `#page-settings` already hosts web-search config. Add
a sibling card "LLM Routing" with five rows:

1. **Default model** — text input + "use env default" hint
2. **Coding model** — text input
3. **Vision model** — text input
4. **Auto-router** — checkbox + 1-line description
5. **Auto-style** — checkbox
6. **Backend tier** — select: `local` / `claude` / `hybrid`
7. **Agent backend** — select: `ollama` / `anthropic`
8. **Agent Ollama model** — text input
9. **Agent Anthropic model** — text input

Each row shows the **current effective value** (DB or env or default)
+ the **env that would take over if cleared**. "Reset to env"
button per row.

Save button writes only the rows the operator touched.

## 8. Non-goals

- **Not changing dispatch logic.** The 4 layers stay. Only the source
  of values changes.
- **No per-user / per-tenant overlay.** The settings are operator-
  global; per-tenant routing belongs to v1.0 multi-tenant work.
- **No live model swap mid-request.** A POST to `/admin/llm-settings/`
  changes future calls; calls already in flight are not interrupted.
- **No automatic env mutation from the UI.** Operators that want env-
  source-of-truth keep the DB row empty.
- **No telemetry / "routing decision explanation" surface.** Already
  available via `audit_log` rows; not a new feature here.

## 9. Migration

- First boot after this PR: DB has no `llm_settings` row → every
  read falls through to env → behaviour byte-identical to pre-PR.
- Operator opens Settings UI, edits → DB rows are written for the
  edited keys only. Untouched keys continue to use env fallback.
- Rollback: drop the table (or delete each row); behaviour reverts
  to env-only.
