# v0.6 — Coding ↔ Retrieval Wiring (design memo)

> **Status: design only.** No code in this PR. This memo answers the
> operator question (2026-06-19): *"추론 능력과 코더 능력은 별개인가?
> 자메스의 추론을 좋게 만들면 코더도 오르는가?"* The honest answer in
> the current build is **no** — and this memo is the concrete proposal
> for the one wiring that would change that, **plus the measurement
> prerequisite that gates it.**
>
> **Scope frame**: a *capability bridge* on top of the existing
> retrieval + coding paths. We do NOT train models, do NOT add a
> vertical/domain feature (rule #1), and do NOT touch the retrieval
> ranking math. We add an opt-in path that lets `handle_coding`
> consult `RetrievalEngine` before the coder LLM call. Behaviour with
> the flag OFF is byte-identical to current main.

## 1. Why they're separate today (the finding)

Two structural facts, both verifiable in code:

**(a) Different model brain.** Coding routes to a coder LLM, chat/RAG
route to gemma:

- `core/reasoning/modes/coding.py:79` → `route(task_type="coding")` →
  `qwen2.5-coder` / `deepseek-coder`
- `core/reasoning/modes/chat.py` → gemma via `trace_synth_call`
- `core/llm_catalog.py` splits `purpose: ["coding"]` from
  `purpose: ["chat","retrieval"]`

**(b) Coding bypasses the entire retrieval pipeline.** This is the
decisive one. Nearly all of JAMES's "reasoning ability" work
(RAG / graph / abstention / evidence-scope / audit) lives in
`run_retrieval_pipeline` (`core/reasoning/engine.py:349`). But the
mode dispatch returns from `handle_coding` *before* it reaches that
line (`engine.py:323-324`), and the coding result is hardcoded:

```python
# core/reasoning/modes/coding.py:144-148
"graph_paths": [], "graph_used": 0, "sources": [],
```

So improving retrieval / graph / abstention does **not** propagate to
the coding path. The two capabilities only converge inside the
*foundation model's* pretraining (code data ↔ reasoning), which is the
model author's domain (Google/Alibaba/Zhipu), not JAMES's.

➡️ **Conclusion:** within JAMES they are separate by construction. The
only lever JAMES owns to couple them is to route retrieval context
into the coder call. That lever is what this memo specifies.

## 2. The two distinct value props (do not conflate)

| | Corpus fed to coder | Prerequisite | Use case |
|---|---|---|---|
| **V-A: knowledge bridge** | existing wiki/knowledge base (what `VectorStore` already holds) | none — corpus exists | coding question references domain facts already in JAMES ("우리 스키마에서 X 필드 타입이 뭐였지? 그거 마이그레이션 코드 짜줘") |
| **V-B: codebase bridge** | the repo's own source files | **new ingestion path** (repo → documents → `VectorStore`) | "edit `foo.py`'s retry logic" with the coder actually seeing the surrounding code |

**Honest caveat:** today's `VectorStore` contains ingested
knowledge/wiki entities, **not** source code. V-A works the moment we
wire the flag. **V-B is the more valuable one but is gated on a
separate code-ingestion path** that does not exist yet. This memo
specs V-A as the shippable unit and scopes V-B as a follow-on.

## 3. Proposed design — V-A (knowledge bridge)

### 3.1 Env gate (mirrors existing JAMES pattern)

New flag `JAMES_CODING_RETRIEVAL`, default **OFF**. Pattern is
identical to `JAMES_AUTO_ROUTER` (`core/reasoning/router.py:76`),
`JAMES_FORCE_CLOUD` (`router.py:88`), and
`JAMES_ADAPTIVE_BUDGET` — opt-in, byte-identical when unset.

```python
def _coding_retrieval_enabled() -> bool:
    return os.getenv("JAMES_CODING_RETRIEVAL", "0").strip().lower() \
        in {"1", "true", "yes", "on"}
```

### 3.2 Wiring point in `handle_coding`

Before the coder LLM call (`coding.py:51` user-pick branch and
`coding.py:78` router branch), when the flag is ON:

```python
context_block, sources = _gather_coding_context(
    safe_query, user_role=user_role, source_type=...,
)   # "" , [] when flag OFF → identical prompt to today
coding_prompt = f"{sys_prefix}{context_block}코딩 질문: {safe_query}\n\n답변:"
```

`_gather_coding_context` calls
`RetrievalEngine().hybrid_search(safe_query, top_k=K,
user_role=user_role, source_type=source_type)`
(`core/retrieval_engine.py:68`) and assembles a bounded context
string. **ABAC is preserved for free** — `hybrid_search` already
filters by `user_role` through `PolicyEngine.can_retrieve`
(`retrieval_engine.py:101-104`), so the coder never sees documents the
caller can't read.

### 3.3 Result + audit (replayability is non-negotiable)

The currently-empty fields get populated so the coding answer is
auditable like every other JAMES answer:

```python
"graph_paths": [], "graph_used": 0,   # V-A: no graph yet
"sources": sources,                   # now real
```

Plus a `trace_synth_call` `applied_rule` already tags the synth step;
add a retrieval trace step so `reconstruct_graph_at(t)` / RAB can see
what context the coder was given. (This is what keeps the bridge
inside JAMES's audit identity rather than a side-channel.)

### 3.4 Module-size gate (rule #5)

`coding.py` is ~5 KB; the context-assembly helper would push it but
not over 20 KB. To stay DRY with the RAG path's context assembly,
`_gather_coding_context` should live in `modes/_common.py` (already
the shared-constants home) or a new `core/reasoning/coding_context.py`
if it grows. Decide at impl time by line count.

## 4. The measurement prerequisite (this is the real gate)

Rule #2: any PR touching `core/reasoning` needs bench numbers + a
Quality Delta Card scored against a baseline. **JAMES has no coding
eval.** Every existing harness — RGB, RAB, QVT, LRB, path-recall,
abstention-F1 — measures *RAG/retrieval* quality. None measures code
correctness. So:

> We cannot prove "retrieval context improves coding" with any
> current baseline. The Quality Delta Card for the impl PR would have
> nothing valid to score against.

Therefore the **honest sequencing** is:

- **P0 (prerequisite):** build a minimal coding eval harness —
  e.g. N coding tasks with executable check (unit-test pass / patch
  applies / output match), paired ON-vs-OFF. Without this, the impl
  is unmeasurable and rule #2 blocks it.
- **P1:** flag + wiring skeleton, default OFF, byte-identical
  (lands safely even before P0 since OFF = no behaviour change; PR is
  `chore`/`docs`-adjacent + a no-op-when-off test).
- **P2:** context assembly + ABAC pass-through + audit trace step.
- **P3:** run P0 harness paired (ON vs OFF), fill the Quality Delta
  Card, decide default. Honest-framing rule applies: report effect
  size, not a ⭐ headline.

This is the same discipline the α-cycle taught — *measure the marginal
contribution before flipping a default.* If P3 shows no lift on V-A,
that's a valid negative result and the flag stays OFF (the
infrastructure is still preserved for V-B / other models, exactly as
the cloud-tier S6/S7 hold was handled).

## 5. Risks / open questions

1. **Corpus relevance (V-A):** is the knowledge base actually
   relevant to coding questions in practice, or is it domain prose
   that adds noise? P3 measures this directly. Likely modest unless
   the operator's KB holds schema/API/config knowledge.
2. **V-B ingestion shape:** if we go to codebase-RAG, what's the
   chunking unit (file / function / symbol)? How does it stay fresh
   on every commit? Separate design memo if V-A proves the pattern.
3. **Patch pipeline interaction:** the auto-patch step
   (`coding.py:120-139`) runs on the coder's answer. Injecting
   retrieval context must not change the patch-extraction contract —
   verify the extractor still parses the answer body.
4. **Token budget:** coder prompts + retrieved context must respect
   the coder model's window (qwen-coder 32B). Bound `top_k` and
   per-doc truncation, mirror the RAG path's caps.
5. **Cloud coder:** if/when a cloud coder backend exists, retrieved
   context = egress. Must route through `core/abstraction/`
   (§5.7.12 Cloud Egress Trust Zone) — same gate as synth.

## 6. Out of scope

- Model training / fine-tuning (JAMES does not train; §non-goals).
- GLM-5.2 or any frontier model — orthogonal; this is corpus wiring,
  not a model swap.
- Any vertical/domain coding feature (rule #1) — this is
  domain-agnostic mother-platform plumbing.
- Rewriting `llm/router.py` task_type dispatch (that's the
  v0.6.1 routing-unification memo's scope).

## 7. One-line answer to the originating question

> Today: improving JAMES reasoning does **not** improve its coder —
> different model + coding bypasses the retrieval pipeline. The
> **only** JAMES-owned lever to couple them is feeding retrieval
> context into the coder call (this memo). It is shippable as an
> opt-in flag, but **must not be defaulted ON until a coding eval
> exists to prove it helps** — building that eval (P0) is the real
> first step.
