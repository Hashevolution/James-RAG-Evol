> 직전 클라우드 세션에서 작성·검증된 핸드오버. PC 세션에서 그대로 참조해 작업 진행.

## Context

v0.1.3에서 모든 LLM 호출이 `RouterWrapper`로 이관된 직후 발생한 회귀로
`core/reasoning_engine.py:920`의 `self.llm.get_cache_stats()` 호출이 500
에러를 발생시킴. 본 문서는 이전 세션에서 작성된 핸드오버 5개 주장을
default 브랜치 코드에 대조해 타당성을 확정하고, 틀린 부분을 바로잡은
후속 진행 순서를 정함.

## ⚠️ Origin & Environment Caveats (반드시 먼저 읽을 것)

본 핸드오버의 관찰 출처는 **PC가 아닌 별도 노트북**입니다:
- 그 노트북에 GitHub에서 신규 clone → 신규 설치 → 가동 시점에 발생한 증상
- Ollama 모델 풀, 하드웨어 사양(RAM/VRAM), `wiki/` 데이터셋, `chroma_db/` 인덱스 모두 PC와 다를 수 있음
- v0.1.2/v0.1.3 릴리스노트의 성능 수치(p50 25.7s → 23.8s, 161 entities, 263 relations 등)는 **노트북 전용** 측정. PC에서 같은 수치 재현 기대 금지

따라서 PART 1·PART 2 항목들은 **환경 독립** (소스코드 사실)과 **환경 의존** (런타임·데이터 사실)으로 나눠 다뤄야 합니다.

## PART 1 — 500 에러 근본 원인 (코드 레벨)

**호출 체인** (default 브랜치, 환경 독립):
- `core/reasoning_engine.py:920` — `stats = self.llm.get_cache_stats()`
- `core/reasoning_engine.py:37-38` — `from llm.router import RouterWrapper` / `self.llm = RouterWrapper("general")`
- `llm/router.py` RouterWrapper 클래스 (~L250-278) — 정의 메서드: `__init__`, `call_gemma`, `call_gemma_vision`, `is_available`. **`get_cache_stats` 없음**
- `core/gemma_client.py:89-100` — 원본 `GemmaClient.get_cache_stats()`는 정상 구현 (`hits`, `misses`, `hit_rate_%` 반환)

### 수정 옵션

**옵션 A — 최소 수정 (RouterWrapper에 passthrough 추가)** ← 권장
```python
# llm/router.py RouterWrapper 클래스에 추가
def get_cache_stats(self) -> dict:
    inner = self._get_llm()  # 또는 현재 routing 결과 client
    if hasattr(inner, "get_cache_stats"):
        return inner.get_cache_stats()
    return {"hits": 0, "misses": 0, "hit_rate_%": 0.0}
```
- 장점: 1파일·5줄 패치. 즉시 핫픽스 가능
- 단점: RouterWrapper가 여러 inner client를 가질 수 있는데 대표 1개 통계만 반환되는 한계
- 환경 영향: 없음 (코드 변경만)

**옵션 B — 근본 수정 (라우터 차원의 통합 캐시 통계)**
- RouterWrapper가 모든 inner client의 cache stats를 집계해 `{client_name: stats, total: ...}` 형태로 반환
- `reasoning_engine.py:920`도 이 새 포맷 가정
- 장점: task_type별 캐시 효율 가시화, #15 admin LLM 선택 페이지에도 노출 가능
- 단점: 변경 범위가 RouterWrapper + 호출자 + (있다면) admin UI까지 확장

**권장**: 옵션 A로 즉시 핫픽스 → v0.1.3.1 패치 릴리스. 옵션 B는 #15와 묶어 v0.2.0.
