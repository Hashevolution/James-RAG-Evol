## Purpose

`reports/promo-assets/gemma4-e4b-cognitive-stages-eval.md` is a public fair-witness report on `gemma4:e4b` failure modes on JAMES v0.3's cognitive stages. The report explicitly **asks for external feedback** (X, dev.to comments, Reddit, GitHub issues). This handover tells the next session how to **route, evaluate, and act on** that incoming feedback without re-deriving the whole context.

Any session continuing this track should be able to read this single page and know:

- where the data lives
- which channels feedback is expected from
- how to interpret each kind of incoming reply
- what code/doc change a given reply justifies (and which ones it does not)

## Decision matrix — how a piece of feedback changes the project

The four hypotheses in the report map to four kinds of actionable feedback:

### Hypothesis A — meta-reasoning capacity at 4 B is the floor

**Confirming feedback** (look for): "We tried gemma4:e4b on a critique-of-a-draft task and got the same empty-response pattern. Bumping to 7B+ variants fixed it." Or: published evals (LMSys, Helm) showing the gap is structural.

**Project response**:
- Keep `gemma3:12b` as the documented default for the cognitive-stage layer.
- Open a follow-up PR for **option A2** (route only the meta stages through a separate `JAMES_LLM_MODEL_META` — let `synth.rag` stay on e4b for its long-context win).
- Do not pursue prompt-side workarounds — they will be marginal.

### Hypothesis B — early stop-token emission

**Confirming feedback** (look for): "We set `num_predict=512` and the same prompts on e4b now return non-empty." Or: Ollama / Gemma 4 chat template bug reports.

**Project response**:
- Patch `core/gemma_client.py` to log the raw Ollama response (token count, stop reason) for empty-response cases — gives us better diagnostics.
- Open a small PR adding `num_predict` and `temperature` overrides per stage if a single setting fixes it.
- File an Ollama issue with the trace.

### Hypothesis C — Korean instruction + English JSON schema confusion

**Confirming feedback** (look for): "We changed our JSON keys to all-Korean (e.g. `재작성된_질의`) and e4b stopped returning empty." Or: anyone reproducing with an all-English version of the same prompt.

**Project response**:
- Try **one experimental prompt** in `core/retrieval/query_rewriter.py` with Korean-key JSON, behind an env flag, to verify.
- If it works: that's a 2 KB diff on each of the 4 affected stage files (`query_rewriter.py`, `planner.py`, `reflect.py`, `verify.py`). Quick win.
- If it doesn't: hypothesis A is more likely.

### Hypothesis D — JAMES side prompt-truncation artifact

**Confirming feedback** (look for): only really verifiable internally — examine the truncated prompt sent to `verify.fact_check` for that one stage and check whether the truncation chopped a JSON example mid-brace.

**Project response**:
- This is a JAMES bug, not a Gemma 4 bug. Even if true, it only explains 1 of the 5 empty responses. So it's a side-issue worth fixing on its own, but **does not invalidate the report's main claim**.
- File this as a separate GitHub issue, fix in a small PR, and footnote the eval report (don't let it muddy the headline).

## When a piece of feedback is *not* actionable here

These categories should be acknowledged in the report (Reader contributions section) but **do not change the project**:

- Replies that swap to a completely different model family (Llama, Qwen, DeepSeek) and report success — interesting but doesn't tell us why Gemma 4 e4b fails.
- "Just use Claude / GPT-4o" — already on the roadmap as Option A2 + the `JAMES_REASONING_BACKEND=claude_code_cli` switch shipped in #305.
- "Your prompts are bad" without a specific change to test — note it, ask the commenter for the specific change, do not refactor speculatively.
