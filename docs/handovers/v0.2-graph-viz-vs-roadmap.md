# Handover — Reasoning Graph Viz vs Neo4j vs Visual Graph Editor (Strategic Comparison)

> **목적**: `/admin/graph` (이번 v0.2 구현) 와 자메스 로드맵의 두 위시리스트 항목
> (Neo4j backend, Visual graph editor) 의 관계를 정리. 셋이 서로 어떻게 다르고
> 어떻게 같이 가는지, 그리고 이번 구현이 미래 둘에 어떤 영향을 미치는지.
>
> **작성 시점**: v0.2 Foundation Hardening, commit `74a74b4` 직후
> **자매 문서**: `docs/handovers/v0.2-reasoning-graph-viz.md` (기술/운영적 핸드오버)
> 본 문서는 **전략/아키텍처 핸드오버**.

## 0. 한 줄 요약

세 항목은 서로 **대체재가 아니라 직교(orthogonal) 관계**.
각자 다른 레이어를 건드리며 셋 다 공존 가능. 이번 구현이 셋 중 가장 가벼운
read-only 레이어라서 먼저 만든 것이 정합성에 부합.

## 2. 레이어 비교표

| 항목 | 레이어 | 방향 | 데이터 소스 | 누가 보나 |
|---|---|---|---|---|
| **이번 구현** (`/admin/graph`) | UI / 옵저버빌리티 | 읽기 전용 | wiki frontmatter (현재 markdown) + `/query/` 응답의 추론 trace | admin (운영자) |
| **Neo4j backend** | 스토리지 | 쓰기/읽기 (DB 엔진 자체) | wiki entity + relations | 시스템 내부 (사용자 직접 안 봄) |
| **Visual graph editor** | UI / 편집 | **쓰기** (CRUD on 온톨로지) | `core/ontology.py:RELATION_TYPES` + 엔티티 스키마 | admin (도메인 모델러) |

## 3. 무엇을 해결하는가

| 항목 | 해결하는 문제 | 안 건드리는 영역 |
|---|---|---|
| **이번 구현** | "추론이 어떻게 흘러갔는지 안 보임" — 디버깅·설명가능성 (Axis 3) | 스키마 정의, 데이터 저장 형식 |
| **Neo4j backend** | "10만+ 엔티티에서 markdown 파일 스캔이 느림" — 스케일 | UI, 추론 로직 |
| **Visual graph editor** | "온톨로지 16종 relation 추가/수정이 코드(`core/ontology.py`)로만 가능" — 비개발자 진입장벽 | 추론 흐름 시각화, 저장소 |

## 4. 구현 의존성 / 리스크

| 항목 | 코드 변경 범위 | 리스크 | 본 구현과의 의존 |
|---|---|---|---|
| **이번 구현** | `core/graph_snapshot.py` (8.4 KB) + 프론트엔드만 | **낮음** — read-only, hot path 미변경 | 완료 (commit `74a74b4`) |
| **Neo4j backend** | `core/graph_engine.py`, `core/wiki_generator.py`, 마이그레이션 도구, Cypher 어댑터 | **높음** — 추론·저장 둘 다 영향, 트러스트 경계 재검토 | 이번 구현은 backend 무관하게 동작. Neo4j 도입 시 `build_snapshot`만 새 backend에서 읽도록 어댑터 추가 (~50 LOC) |
| **Visual graph editor** | 새 admin 페이지 + 쓰기 API + PolicyEngine 통과 검증 + 자기진화 게이트 연동 + 감사로그 + 롤백 | **중-높음** — 쓰기 작업이라 ABAC/감사로그/롤백 다 필요 | 이번 구현의 시각화 컴포넌트(노드·엣지 렌더링) **약 70% 재사용 가능** |

---

## 5. 비유 — 도서관

자메스 = 도서관이라고 치면:

- **Neo4j backend**: 책장(저장 시스템)을 종이 메모 카드 시스템에서 정밀한
  라이브러리 시스템으로 교체. 사용자는 책 찾는 속도 빨라진 것만 체감.
- **Visual graph editor**: "책 분류 체계(듀이 십진분류) 자체를 GUI로 편집"하는
  사서 도구. 시스템 운영자가 분류 카테고리를 추가/이동.
- **이번 구현** (`/admin/graph`): "방문자가 어떤 질문을 했을 때 사서가 어느
  책장 → 어느 책 → 어느 페이지로 다녀왔는지" 천장에서 내려다보는 CCTV.
  책장 자체도, 분류 체계도 안 건드림.

---

## 6. 이상적인 시퀀스

자메스 로드맵에서 셋을 다 한다면:

```
이번 구현 (지금, v0.2)
   ↓ (검증된 시각화 컴포넌트)
Visual graph editor (v2.0+)
   - 시각화는 재활용, 위에 편집 모드만 얹음
   ↓ (편집된 온톨로지가 거대해진 뒤)
Neo4j backend (post-v1.0)
   - 스토리지 교체. UI/편집기는 그대로 유지
```

근거:
- 이번 구현이 셋 중 **가장 가벼운 read-only 레이어** → 먼저 만들기에 부합
- Visual graph editor부터 만들었으면 ABAC·자기진화 게이트·롤백·감사로그 전부 같이 와야 함 → v0.2에서 불가
- Neo4j부터 했으면 더 무거운 마이그레이션 작업이 우선 → 가시적 가치 늦게 나옴

## 7. 미래에 끼치는 영향 (이번 구현의 부수효과)

| 영역 | 영향 |
|---|---|
| **Neo4j backend 도입 시** | `build_snapshot`만 Cypher 어댑터로 갈아끼우면 UI는 그대로. backend 결정에 종속되지 않음. ~50 LOC 추가로 끝. |
| **Visual graph editor 도입 시** | 노드/엣지 렌더링·hover·클릭·구형 force layout·검색 필터 이미 있음. 편집 모드(드래그로 엣지 생성, 우클릭 메뉴, 변경 미리보기)만 얹으면 됨. **약 70%가 재사용 가능**. |
| **사회적 압력** | `/admin/graph`가 admin들에게 "구조를 시각적으로 볼 수 있다"는 기대를 만들어버려서, 나중에 Visual graph editor에 대한 자연스러운 요구가 올라옴 (좋은 의미의 압력). |
| **데이터 모델 안정화** | 시각화가 `entity_type`, `relations[].type`, `relations[].confidence` 같은 필드에 직접 의존하므로, 이 필드들이 **사실상의 공식 contract**로 굳어짐. 이후 Neo4j 마이그레이션 시 스키마 흔들림 줄어듦. |

---

## 8. 무엇을 하지 않았는가 (의도적 미포함)

이번 구현은 다음을 **하지 않음** — 위 직교 관계를 유지하기 위함:

- ❌ 엔티티/관계 편집 — Visual graph editor 영역
- ❌ 새 저장 포맷 정의 — Neo4j backend 영역
- ❌ Cypher 비슷한 쿼리 언어 — Neo4j backend 영역
- ❌ 추론 로직 변경 — `core/reasoning/*` 미수정 (Axis 2/3 분리 원칙)
- ❌ 온톨로지 스키마 변경 — `core/ontology.py:RELATION_TYPES` 미수정

## 9. 다음 세션이 받을 질문 / 결정 포인트

향후 다른 Claude Code 세션이 이 결정 트리에서 마주칠 분기:

| 사용자가 요청하면 | 적절한 응답 |
|---|---|
| "그래프에서 엔티티 직접 편집되게 해줘" | Visual graph editor 영역. v2.0+ 위시리스트. v0.2 mother-hardening에서는 불가. PolicyEngine + 자기진화 게이트 + 감사로그가 같이 와야 함. |
| "Neo4j 붙여줘" | Beyond v1.0 — Speculative. 현재는 markdown frontmatter로 충분. 엔티티 10만+ 가 되면 다시 평가. 이번 구현(`build_snapshot`)에 어댑터 패턴 추가하면 UI는 그대로 살아남. |
| "그래프 viewer 자체 기능 보강" (필터, 검색, LOD 등) | 이번 구현의 자연 확장. v0.2 안에서도 가능. 단 사이즈 게이트(`core/`는 20 KB) 유지. |
| "벡터 임베딩까지 시각화" (UMAP/t-SNE 등) | 별도 결정 사안. 이번 구현은 그래프 토폴로지만 보여주고, 벡터 거리는 안 보여줌. 추가 시 ChromaDB → 차원축소 파이프라인 필요 (성능 고려). |

## 10. 결론

사용자가 직관적으로 **가장 위험 적고 재사용 가능한 부분을 골라낸 것**. 로드맵의 두
큰 항목 (Neo4j backend, Visual graph editor) 으로 가는 길에 자연스럽게 깔리는
디딤돌 역할이며, 두 항목 어느 쪽이 먼저 와도 호환되는 인프라.

v0.2 mother-platform 룰을 어기지 않으면서 v2.0+ 위시리스트의 시각화 측면을 한
세션 안에 끌어왔다는 점에서, 시점적으로도 정합성 있는 선택.
