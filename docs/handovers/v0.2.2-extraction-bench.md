## 1. Why this cycle exists

The v0.2 Axis 2 harness (STEP 7 + RAGAS) measures **consumption-side
quality** — answer faithfulness, context precision, graph paths
retrieved per query. It does not measure **extraction-side quality** —
how good the graph itself is, independent of how it gets used.

Issue #6 (relation label distribution skew, RELATED_TO = 91%) is the
canonical example of why this gap matters. The issue was closed
2026-05-07 with a prompt-side fix in `core/wiki_generator.py:691–698`
(explicit type-pair → label hints + "use 관련 only when nothing else
fits"). The fix is committed and live. **What is missing is the
numeric confirmation that the fix actually moved the distribution,
and a regression sentinel that catches reversion.**

Beyond #6, we have no single number that tracks extraction quality
across runs, and no reference point to decide whether the current
local extractor is "good enough" or whether a different extractor
(larger local teacher model, or opt-in cloud LLM per the deferred
ARCHITECTURE discussion) is justified. This cycle produces both the
sentinel and the reference point.

## 2. The decision this cycle must enable

Two binary gates, evaluated from measurement output alone:

- **Gate G1 — fix sufficiency**: did the closed Issue #6 prompt fix
  actually re-balance the relation label distribution?
- **Gate G2 — extractor swap value**: if not, is the gap large enough
  to justify a heavier extractor (local 72B teacher, or opt-in cloud)?

Gate definitions appear in §7. G2 only fires if G1 indicates the fix
fell short.

## 4. The five metrics

| # | Metric | Definition | What it isolates |
|---|---|---|---|
| M1 | Entity P/R/F1 | Against golden set | Extractor omissions/over-extraction |
| M2 | Relation triple P/R/F1 | Against golden set triples | Relation accuracy, independent of M1 |
| M3 | Relation-label entropy | Shannon / log(N_labels) | Issue #6 skew as a single number (0..1) |
| M4 | k-hop reachability (k=2,3) | % of random node pairs with k-hop path | Multi-hop query feasibility |
| M5 | STEP 7 + RAGAS deltas | Existing harnesses, post-reindex | Whether extraction gains translate to answers |

M1–M4 measure the graph itself. M5 measures the consequence. Both
are required: a graph can improve on M1–M4 without M5 moving, and the
PR-contract (CLAUDE.md rule #2) only accepts changes whose M5 numbers
are pasted.

M3 carries dual duty as **the regression sentinel** for Issue #6.
Once baselined, any extraction-side change must hold M3 ≥ baseline
or paste justification.

## 5. The golden set

Single human-labeled artifact. Without it, M1/M2 are not computable.

- **Path**: `eval/extraction/golden_v0.2.json` (new)
- **Size**: 20 source documents (~12% of the 161-entity corpus)
- **Schema**: per-document `{entities: [...], triples: [{s, r, o}, ...]}`
- **Selection**: documents that feed STEP 7 queries #2, #3, #5, #6
  (so M5 has direct causal traceability to M1–M4)
- **Labeling**: single operator, ~4–6 hours. Inter-annotator agreement
  measured on 5 documents only (single-operator deployment context)
- **Labeling guide**: 1-page doc — what counts as an entity, when to
  use RELATED_TO vs a more specific relation. The guide itself becomes
  the prompt template for any future LLM-based extractor.

## 6. Three extraction passes

| Pass | Extractor | Cost | Purpose |
|---|---|---|---|
| A | Current local (baseline, includes #6 fix) | 0 | Absolute baseline for M1–M5 + G1 evaluation |
| B | Larger local teacher (e.g. qwen2.5:72b) | 0, time-heavy | G2: can we close any remaining gap without ARCHITECTURE change? |
| C | Cloud LLM, opt-in test only | ~$15, single run | G2: upper bound for what extraction quality can reach |

Pass C is **measurement-only**, off the deployed code path, on
already-anonymized golden-set documents. It does not introduce a
runtime cloud dependency. The output is data, not a feature.

## 7. The decision gates

Run all three passes against the same golden set, then apply in order:

```
Gate G1 — fix sufficiency
  M3(A) ≥ 0.60  →  Issue #6 fix verified working. Close G1, lock M3
                   as regression sentinel. Skip G2.
                   (0.60 ≈ 12 ontology labels, dominant ≤ ~40%.
                    Provisional; refine after A-pass observed.)
  M3(A) <  0.60 →  Fix insufficient. Proceed to G2.

Gate G2 — extractor swap value (only if G1 fails)
  (B − A) ≥ Δ        → Local teacher closes gap. No ARCHITECTURE
                       change. Adopt as new baseline.
  (C − A) <  1.5×Δ   → Cloud adds insufficient value over current
                       local. Keep status quo. Close cloud-extraction
                       discussion.
  (C − A) ≥ 1.5×Δ
   AND (C − B) ≥ Δ   → Cloud adds value over both. Open formal
                       ARCHITECTURE discussion using these numbers
                       as evidence.
```

Δ defined as **all three** of: F1 +0.10, M3 +0.20, M4 +15pp.
Tighter than per-metric thresholds intentionally — extraction
changes that move only one axis are not worth the cycle cost.

Numbers may be revised once A-pass is observed (some metrics may
have less headroom than expected).

## 8. Recommended task order

In order. Do not jump unless blocked.

### P0 — Golden set + labeling guide
- `docs/eval/extraction-labeling-guide.md` (new, 1 page)
- `eval/extraction/golden_v0.2.json` (new, 20 docs)
- Single operator. Estimate: 0.5 day for guide, 0.5–1 day for set.

### P0 — Measurement code
- New bench suite: `scripts/bench.py --suite=extraction_quality`
- Reads golden set + a graph snapshot, emits M1–M4 JSON
- Reuses existing `bench.py` CLI / report / baseline conventions
- Estimate: 1 day.

### P0 — A-pass execution + baseline commit
- Run current local extractor on the 20 documents, build graph
  snapshot, compute M1–M4
- Commit baseline to `eval/extraction/baseline_v0.2.json`
- Re-run STEP 7 + RAGAS for M5 reference
- **G1 evaluated here. If passed, P1/P2 below become optional.**
- Estimate: 0.5 day.

### P1 — B-pass execution (only if G1 fails)
- Configure local 72B teacher via Ollama
- Same input, same metrics
- Estimate: 0.5–1 day (model download dominates).

### P1 — C-pass execution (only if G1 fails)
- Anonymize the 20 documents (operator review pass)
- Single cloud-API extraction run; result is a JSON file
- Compute M1–M4
- Estimate: 0.5 day.

### P0 — Decision document
- `docs/decisions/v0.2-extraction-engine.md` (new)
- Single page: numbers, gate evaluation, decision
- Re-opens or confirms-closed Issue #6 with the numeric verdict
- Estimate: 0.5 day.

**Total: ~3 days if G1 fails, ~1.5 days if G1 passes.** Fits one cycle either way.

## 9. Things this cycle deliberately does NOT do

- Do not introduce a runtime cloud dependency. Pass C is offline
  measurement only — never wired into the deployed extractor.
- Do not implement automated PII anonymization. The 20 golden docs
  are operator-reviewed before pass C. Anonymization is an
  out-of-scope follow-up if cloud extraction is later adopted.
- Do not implement Entity Resolution between A/B/C outputs. Each
  pass is measured independently against the same golden set.
  Cross-pass merging belongs to a separate cycle if it ever happens.
- Do not modify `scripts/bench.py` STEP 7 baseline. M5 reference
  numbers go into a side file, not the locked baseline.
- Do not extend to non-Korean/English content. Current corpus scope.
- Do not retroactively re-open Issue #6 before A-pass. The closure
  stands until the data says otherwise.

## 12. 한국어 요약

v0.2.2 사이클은 STEP 7·RAGAS가 다루지 않는 **추출-측 그래프 품질**을
정량 측정합니다. Issue #6(2026-05-07 closed)의 프롬프트 수정이
`core/wiki_generator.py:691–698`에 들어 있지만 정량 검증은 없습니다.
이 사이클의 1차 목적은 **그 수정의 실효성 확인(G1)**, 2차 목적은
G1 실패 시 **로컬 teacher / 옵트인 클라우드 추출의 도입 가치 판단(G2)**
입니다. 5개 지표(M1 엔티티 P/R/F1, M2 관계 P/R/F1, M3 라벨 엔트로피,
M4 k-hop 도달성, M5 STEP 7+RAGAS 회귀)를 골든 셋 20문서에 대해
3개 추출 패스(현 로컬 / 로컬 72B teacher / 클라우드 측정-전용)로
비교합니다. G1 통과 시 ~1.5일, 실패 시 ~3일. 코어 코드 변경 없음,
런타임 클라우드 의존 없음. M3는 향후 추출 변경의 영구 회귀 지표로
정착됩니다.
