## 0. 한 줄 요약

JAMES 의 cognitive middleware (planner / reflect / verify / tool_router) 는 코드는
있지만 **opt-in 상태로 부하가 없어** 효용 입증이 안 되어 있다. 본 트랙은
세 가지 승부처 — **(Q1) 각 stage 안정성**, **(Q2) verifier 의 hallucination
감소량**, **(Q3) planner 가 실제 reasoning depth 를 늘리는지** — 를 숫자로
못박는 측정 인프라를 먼저 깔고, 그 다음 stage-specific PEFT 로
**"cognitive runtime"** 화한다. 도메인 분화·자동 self-improvement 는
v1.0 이후로 명시 연기.

## 1. 배경 — 외부 평가 2건 요약

### 1.1 평가 #1 (구조·아키텍처)
JAMES 는 "보안 + 온톨로지 + Graph-RAG + 추론 통제 + 자기진화 scaffold" 를
한 구조로 묶은 드문 시도. 강점:
- 보안이 파이프라인 *내부*에 있음 (RBAC+ABAC+instruction isolation)
- 온톨로지가 security boundary + reasoning path 로 쓰임
- 감사/추적/staged evolution discipline

약점:
- 깊은 multi-hop reasoning, planning, abstraction, self-reflection,
  memory compression, causal inference 부족
- "Graph = intelligence" 착각 위험
- 정적 ontology
- episodic / semantic / procedural memory 분리 없음

진단: **"보안형 Graph-RAG 운영 플랫폼 Alpha"** 에 가깝고, "강한 추론
엔진" 으로 진화 필요.

### 1.2 평가 #2 (Fine-tuning · cognitive runtime)
JAMES 는 단순 LLM 하나가 아니라 stage 들이 분리되어 있으므로 **stage 단위
PEFT** 가 가능. 일반 RAG fine-tuning 과 달리:
- planner / verifier / critique / ontology extraction 각각 튜닝 가능
- runtime trace 가 그대로 cognition dataset 의 source
- "RAFT" (Retrieval-Augmented Fine-Tuning) 구조에 잘 맞음

권장 우선순위: embedding → reranker → verifier → planner → synthesis.

### 1.3 코드 실측과의 대조
평가자들은 일부 기능을 누락 인식 — 실제로는 이미 존재:

| 평가 지적 | 코드 실측 | 진짜 격차 |
|---|---|---|
| "Planner 없음" | `core/reasoning/planner.py` 347줄, **OPT-IN**, 에러 시 single-subtask fallback | 활성화 휴리스틱·tool router 연결·default-on 기준 |
| "Critic/Verifier 없음" | `reflect.py` 349줄 + `verify.py` 479줄, 둘 다 **OPT-IN**, 15–20s 오버헤드 | 비용 절감·정확도·hallucination gold set |
| "Memory OS 없음" | SQLite 단일 평면 (`preferences/patterns/goals`) | episodic/semantic/procedural 분리, temporal index, decay |
| "Ontology 정적" | 16 relation 하드코딩 | CR-E 기반 ontology 진화 파이프라인 |
| "Tool Router 무력" | `tool_router.py` 398줄, *"MVP wiring is zero"* (주석) | 실제 dispatch 연결 |
| "Trust-weighted memory 없음" | `trust.py` 321줄 (wiki write 만) | retrieval/memory 전역 확장 |

**핵심**: 인프라는 깔려 있다. 부하가 안 걸려 있다. → 측정 우선.

## 2. 승부처 — 세 가지 측정 질문

세 질문을 falsify 가능한 metric 으로 환원하는 것이 본 트랙의 1차 산출물.

| 질문 | 조작적 정의 | 핵심 metric |
|---|---|---|
| **Q1. stage 안정성** | "trace row 가 schema-valid 하고, fallback 분기로 빠지지 않고, p95 latency 가 budget 안" | `stage_health = valid × ¬fallback × ¬timeout` per stage |
| **Q2. verifier hallucination 감소** | "verify ON/OFF 동일 질의쌍에서, hallucinated answer 가 block/annotate 로 잡히는 비율 − 정상 답을 false-positive 로 차단한 비율" | `Δhallucination_rate = H_off − H_on`, `FPR_correct ≤ ε` |
| **Q3. planner depth 증가** | "단발 RAG 가 실패하는 multi-hop set 에서 planner ON 의 정답 회수율 증가. **단순 subtask 수 ≠ depth**" | `Δaccuracy_multihop`, 보조: `evidence_diversity`, `graph_hop_count` |

**디자인 원칙**: 절대값(예: "verify ON 92%")은 정보가 거의 없다. 같은 query
셋을 양 조건에 통과시킨 **paired A/B 차이값**만 의미 있음.

## 3. Measurement Battery (Phase 0)

### 3.1 Plan A — Stage Reliability Harness (Q1)

| 구성요소 | 정의 |
|---|---|
| **Stage Health Card** | stage 당 한 줄: `{stage, calls, schema_valid_%, fallback_%, error_%, p50_ms, p95_ms, budget_violation_%}` |
| **Source of truth** | `audit_log` 에서 `endpoint LIKE "reason:%"` 필터. **신규 DB 테이블 추가 없음** |
| **Pass 기준 (제안)** | `fallback_% ≤ 5`, `schema_valid_% = 100`, `p95 ≤ stage_budget` (planner 8s / reflect 8s / verify 3s / 나머지 1s) |
| **운영 형태** | `scripts/stage_health.py --window 7d` → markdown 표 출력. PR description 첨부 |
| **회귀 게이트** | reasoning/retrieval PR 머지 시 stage 별 `fallback_%` 가 baseline + 2pt 초과면 빨간불 |

**왜 첫 번째인가**: Q2/Q3 결과가 신뢰되려면 그 안의 stage 들이 honest 하게
동작 중이라는 게 전제. planner 가 사실 fallback (single-subtask trivial plan)
으로 빠지고 있다면 Q3 측정은 거짓말.

### 3.2 Plan B — Hallucination A/B Harness (Q2)

#### B-1. Gold set 구축
저장 위치: `eval/hallucination/gold_v1.json` (도메인 중립 — rule #1 준수).

| 분류 | 크기 (제안) | 출처 |
|---|---|---|
| **truthful** (정상 답 가능, 차단되면 안 됨) | 50 | STEP 7 + RAGAS fixture 재사용 |
| **bait-hallucination** (ground-truth = "정보 없음") | 30 | 신규 — "당사 2027년 매출은?" 같은 미래/허구 질의 |
| **trap-mix** (context 안에 정답·오답 동시 삽입) | 20 | 신규 |

항목당: `{query, expected_verdict, expected_answer_substring?, trap_facts?}`.

#### B-2. Harness 실행
```
matrix = (verify=OFF, verify=heuristic_only, verify=full_with_factcheck)
        × gold_set
```
3 × 100 = 300 회. ollama_local 기준 ~30분.

#### B-3. 산출 지표

| 지표 | 합격선 |
|---|---|
| `block_precision` | ≥ 0.85 |
| `block_recall` | full ON 에서 ≥ 0.6 |
| `truthful_FPR` | ≤ 0.05 |
| `Δquality_annotated` (RAGAS faithfulness) | ≥ +0.05 |
| **종합 판정** | `recall − 2×FPR > 0` 이면 default-on 후보 |

#### B-4. 결과 → 의사결정

| 결과 | 행동 |
|---|---|
| recall 낮고 FPR 낮음 | verify 가 너무 보수적 → fact-check prompt 강화 |
| recall 높고 FPR 높음 | over-blocking → heuristic layer rule 좁히기 |
| 둘 다 낮음 | verify.py 사실상 무력 → 재설계 후보 |
| 둘 다 좋음 | default-on (env flag 제거) |

### 3.3 Plan C — Reasoning Depth A/B Harness (Q3)

#### C-1. "depth" 의 함정 회피
`subtask_count` 만 보면 planner 는 항상 이김 (5개 subtask 우겨내면 됨).
**세 채널 동시 측정**:

| 채널 | 측정 | 의미 |
|---|---|---|
| (a) **Outcome** | multi-hop gold set 정답률 | 진짜 풀었는가 |
| (b) **Process** | distinct entity hop 수, distinct retrieval call 수, evidence source 다양성 | 정말 다단계로 갔는가 |
| (c) **Cost** | latency, LLM token | 비용 대비 효용 |

**Depth 판정**: (a) 가 통계적으로 유의하게 상승하고 (b) 가 동반 상승할 때만
진짜 depth. (a) 변화 없는데 (b) 만 오르면 **공허한 다단화** (= "Graph =
intelligence 착각" 의 LLM 버전).

#### C-2. Multi-hop gold set
저장: `eval/multihop/gold_v1.json`. **도메인 중립 코퍼스**.

| 분류 | 크기 | 정의 |
|---|---|---|
| `single_hop` | 30 | 1-entity — planner 우회 시 패널티 |
| `2_hop` | 30 | A→B→answer |
| `3_hop` | 20 | 단발 RAG 가 거의 실패하는 chain |
| `compare` | 10 | "A vs B" 병합 |

#### C-3. 비교 매트릭스
```
conditions = {
  baseline_RAG,             # planner OFF, reflect OFF
  planner_only,             # planner ON, reflect OFF, tool OFF
  planner_plus_tool,        # planner ON + tool_router 실배선
  full_cognitive            # planner+reflect+verify+tool 전부 ON
}
× gold_v1 (90 queries)
```

#### C-4. 합격 기준

| 항목 | 목표 |
|---|---|
| `Δaccuracy_2hop` (planner_only vs baseline) | ≥ +10pt |
| `Δaccuracy_3hop` | ≥ +15pt |
| `Δaccuracy_single_hop` | **0 ± 3pt** (단발 질의 회귀 금지) |
| `latency_overhead_p50` | full_cognitive ≤ baseline × 3 |
| `evidence_diversity` | planner_only ≥ baseline × 1.5 |

**Falsifier**: accuracy 회귀 없이 못 올리면 planner 는 현재 형태로는 가짜
depth. 회수 못 하는 hop 증가는 **버그 신호**.

### 3.4 세 하네스의 종속관계

```
Plan A (stage reliability)
   │  stage 가 fallback 안 빠지는 게 확인된 다음에야
   ▼
Plan B (hallucination)  ⊥  Plan C (depth)   ← 병렬 가능
   │                       │
   └─── 두 결과 합쳐서 ────┘
              ▼
   default-on / opt-in 유지 / 재설계 결정
```

A 가 빨간불인데 B/C 돌리면 결과 신뢰 못 함.

## 4. Cognitive Runtime Tuning (Phase 1–7)

### 4.1 비전 채택, rule 정합

평가 #2 의 **"cognitive runtime tuning"** 비전 채택. 단:
- 도메인 PEFT (legal/security/policy) 는 **rule #1 위반** → v1.0 이후
- "self-improving loop" 는 **rule #3 위반 가능** → **"human-gated cognitive
  promotion"** 으로 재정의 (모든 adapter swap = CR-E)
- **도메인 중립 stage tuning** (planner / verifier / reranker 일반 추론
  능력) 은 mother-hardening 의 일부 → 허용

### 4.2 Phasing

| Phase | 작업 | 게이트 |
|---|---|---|
| **0** | Measurement battery (§3) | prerequisite — 이게 끝나야 다음 단계 의미 있음 |
| **1** | **Trace Harvest 인프라**: verifier 통과한 trace 를 `eval/cognition_traces/` 로 저장. 항목당 `{query, plan, retrieval, critique, verdict, final, verifier_confidence}`. **labeled-only 저장 원칙** | rule #1 (도메인 중립), 개인정보 mask |
| **2** | **Reranker LoRA** (cross-encoder). 가장 안전·고ROI·도메인 중립. STEP 7 multihop 에서 nDCG@10 +X% 목표 | rule #2 bench, Adapter Registry 통과 |
| **3** | **Verifier LoRA** — Phase 0 hallucination gold 로 학습 | Q2 baseline 잠긴 다음에만. FPR ≤ 0.05 회귀 금지 |
| **4** | **Planner LoRA** — Phase 0 multihop gold + verifier-검증 trace 로 학습 | Q3 baseline 잠긴 다음에만. single-hop 회귀 0 ± 3pt 강제 |
| **5** | **Synthesis LoRA** | 마지막 — 가장 안 건드리는 게 안전. format fixation 위험 |
| **6** | **Gated cognitive promotion**: failure trace → 후보 dataset 자동수집 → CR-E 로 PEFT 제안 묶음 → admin 승인 → adapter promote | rule #3 핵심. `approver_username` 없는 promote 차단 |
| **7 (v1.0 이후)** | **도메인 PEFT** (legal/security/policy) | rule #1 해제 후, 도메인 팩 분기와 동시 |

### 4.3 우선순위 보정 (평가 #2 와 다른 점)

평가 #2 는 "embedding → reranker → verifier" 순서를 제안했지만, JAMES
특화로는 **reranker > embedding**:
- JAMES 는 hybrid retrieval (vector + graph + relation) — embedding 단독
  개선은 graph-path 점수 결합부에 잠식됨
- cross-encoder reranker (`v0.3-cognitive-layer-track.md` Phase 1 PR-1) 는
  이미 default-on → 가장 선명한 lever

### 4.4 데이터 팩토리의 choke point

```
labeled_trace_yield = verify_on_rate × verifier_precision × verifier_recall
```

- 현재 verify 는 OPT-IN, 호출률 거의 0 → yield ≈ 0
- 데이터 팩토리 가동 = verify default-on + verifier 신뢰성 prerequisite
- **Phase 3 (Verifier LoRA) 가 사실상 데이터 팩토리의 모터**

→ Phase 2 (Reranker) 와 Phase 0→3 트랙은 **병렬 진행** 권장:
```
Phase 2 (Reranker, 빠른 win)  ─┐
                                 ├→ Phase 3 시작 가능
Phase 0 결과 (verifier baseline) ┘
```

## 5. Adapter Registry — 필수 신규 primitive

Phase 2 이후의 모든 PEFT 가 의존하는 1차 primitive. 빠지면 전부 무너짐.

### 5.1 위치 (제안)
```
core/reasoning/adapters/
  registry.py        # backend_id × stage → adapter_id 매핑
  manifest.py        # adapter 당 {sha256, base_model, train_data_hash, bench_snapshot}
  promote.py         # CR-E 경유 promote/rollback
```

### 5.2 규칙
- adapter swap = Change Request 1건 (rule #3)
- manifest 에 **학습 데이터 hash + bench 결과** 강제 첨부 (rule #2 의
  PEFT 버전)
- 동일 stage 에 여러 adapter 공존 → A/B 가 그대로 production 게이트
- rollback = manifest 이전 row 로 단순 swap

### 5.3 trace 연결
- `backend_id` 의 자매 개념. backend = 어디서 호출, adapter = 어떤 가중치
- 둘 다 trace row 에 박힘 → replay 가능 (§5.7.2 trace-replay invariant 유지)

## 6. 위험과 가드레일

| 위험 | 가드레일 |

| Planner PEFT 가 reasoning 일반화 손상 | training set 의 60% multihop, 40% single-hop 보존. single-hop 회귀 게이트로 promote 차단 |

  이 들어가는 후속 트랙
